## 第 1 章 · 先看全局：这个项目到底在干什么

### 1.1 一句话

> 把学校的制度文件（校规、通知、办事指南）丢进一个文件夹，
> 然后你就能用**大白话**提问，它会给你一个**带出处**的回答；
> 如果资料里根本没有这事儿，它会**明说"不知道"**，而不是编一个。

### 1.2 它为什么值得存在

你去问任何一个大模型"南海校区宿舍几点关门"，它很可能给你编一个答案，
或者反问你"哪个学校？"。

原因不复杂：**模型不知道你们学校的规定，但它在被训练时学会了"无论如何都要给出像样的回答"**。
这个"必须回答"的习惯，在政策问答场景里会直接变成事故——学生会照着编出来的规定去办事。

所以本项目的核心不是"让模型更聪明"，而是：

> **先在你的资料里把证据找出来（检索），证据不够就闭嘴（拒答），
> 证据够才让它说话，并且每句话都要挂上出处编号（引用）。**

### 1.3 一句话技术方案

**"先检索、后生成、带引用、可拒答"**。

换成生活场景：

| 角色 | 对应代码 | 干什么 |
| --- | --- | --- |
| 图书管理员 | `data.py` | 把一堆文件拆成一张张"资料卡"，每张卡写清它属于哪一章 |
| 两套索引目录 | `retriever.py` | 一套按关键词找，一套按字面相似找，最后把两边的结果合并排序 |
| 一位**很谨慎的门卫** | `engine.py` 的闸门 | 打分低于及格线，直接拦住："这个我们资料里没有。" |
| 一位**只会照本宣科的讲解员** | `engine.py` 的生成 | 拿资料原文组织语言，一句一引 |
| 一位**只会读稿的替补** | `engine.py` 的抽取式降级 | 讲解员请假（没网/没 key）时，直接念原文，绝不自由发挥 |
| 质检员 | `evaluate.py` | 出一张 22 题的卷子，把上面每个环节的表现变成百分比 |

### 1.4 它现在真实的水平（实跑数据）

```
$ python ask.py --eval --quiet

【检索质量】—— 决定 RAG 效果的上限
  Hit@3（答案所在文档被召回的比例） : 100.0%
  Hit@1（排在第一位的比例）         : 81.2%
  MRR（平均倒数排名，越接近 1 越好） : 0.896

【拒答能力】—— 没料时敢不敢说不知道
  拒答准确率（该拒/不该拒判断对的比例） : 77.3%
  该答却拒答率（过度保守，越低越好）     : 31.2%
  没料却硬答率（幻觉风险，越低越好）     : 0.0%

【答案质量】
  关键事实覆盖率（数字/术语命中） : 62.5%
  延迟 p50 / 均值                 : 2-3 ms / 题
```

> ⚠️ **关键事实覆盖率是 62.5%，不是 81.2%**——这个数字在 2026-10-06 被修正过。
> 原来报 81.2% 是被一个 bug **刷出来的**：拒答的正文里会原样引用检索到的候选片段，
> 而覆盖率是在整段回答上做词面匹配，于是 `n09`/`n11`/`n14` 三条**该答却拒答**的题
> 反而各记了 100% 覆盖。现在拒答一律计 0。详见第 13.6 与 16.x 节。
> （顺带：Hit@1 也恰好是 81.2%，两者数值相同**纯属巧合**。）

先记住这三个数字的**关系**，这是全项目的价值观：

- **硬答率 0.0%** 是底线（"资料里没有却硬答" = 事故）；
- **拒答准确率 77.3%** 是第二个目标；
- **漏答率 31.2%** 是达成上面两条**必须付出的代价**。

后面你会看到：整本书里几乎每一个"为什么这么写"的答案，
最后都会回到这句话——**宁可拒答，绝不硬答**。

## 第 2 章 · 三个名词：RAG / 检索 / 拒答

### 2.1 RAG 是什么（Retrieval-Augmented Generation）

中文叫"检索增强生成"。拆开看：

- **Retrieval（检索）**：从你的资料里找出和问题最相关的几段话；
- **Augmented（增强）**：把这几段话塞进给大模型的提问里，当作"参考资料"；
- **Generation（生成）**：大模型**只根据这份参考资料**回答。

不用 RAG 时，你问的是："南海校区宿舍几点关门？"
用了 RAG，你问的变成：

```
【资料】
[1] 来源：08-...md · 宿舍管理与生活秩序 > 门禁与作息
- 宿舍大门每日 06:00 开门；周日至周四 23:00 关门熄灯，周五、周六及法定节假日 23:30 关门。

【问题】
南海校区宿舍晚上几点关门？周五周六和法定节假日会延后吗？

请按规则作答。
```

模型这时候不需要"知道"你们学校的规定，它只要**读懂这段资料并组织语言**。
事实来自资料，模型只负责表达——这就是"增强"。

### 2.2 为什么光有 RAG 还不够：幻觉的下半场

很多人以为接上 RAG 就万事大吉了。实际上会出现一个新问题：

> 检索这一步永远会返回"前 4 名"——**哪怕这 4 段话跟问题毫无关系**。

因为排序算法的工作是"把 63 个块按相关度排队"，它**不会说"全都不相关"**，
它只会把最不像的排到最后，然后把最像的那个送到第一。

于是"南海校区游泳池开放时间"（语料里没有游泳池）这个问题的检索结果长这样（实跑）：

```
候选1 09-通知公告问答.md · 常见问题：…0 元）。CET6 需四级 ≥ 425 分…
候选2 08-校规校纪问答.md · 生活服务 > 图书馆（南海校园）：- 开放时间：大厅、新书展厅…
候选3 08-校规校纪问答.md · 生活服务 > "一站式"学生社区综合服务中心：- 位置：熹园餐厅南面…
```

三条都和游泳池无关，但里面都有"开放时间""收费"这些字眼。
如果直接把这堆东西丢给大模型，它会**很努力地**从"图书馆开放时间"里凑一个回答给你。

**所以本项目最重要的一处设计出现了**：在把资料交给模型之前，先算一个"到底够不够格回答"的分数，
不够就直接拒答。这个机制叫**拒答闸门（abstention gate）**。

### 2.3 检索的两种思路，为什么本项目两个都要

你可能会想："找相关资料"不就是搜关键词吗？是，但只做关键词会漏掉大量问题。

| 问法 | 文档里的原话 | 纯关键词能找到吗 |
| --- | --- | --- |
| 旷课多少节会被警告处分？ | 旷课 12 学时 或 擅自离校 3 天 → 警告 | ✅ 有"旷课""警告" |
| 最多能借几本书？ | 可借册数 | ❌ 一个共同词都没有 |
| 图书馆闭馆前提前多久清场？ | 各借阅室、阅览室结束前提前 10 分钟清场 | ✅ 有"提前""清场" |
| 要什么材料、什么时候交？ | 材料在 3.1 节，时间在 3.4 节 | ⚠️ 一半一半 |

所以本项目做了两条**互补**的通道（第 8 章详解）：

1. **词法通道（BM25）**：传统搜索算法，擅长精确术语和数字（"12 学时""FM75""15 公里"）；
2. **向量通道（字符 3-gram TF-IDF）**：擅长模糊改写，因为它只看"字符片段有没有重叠"。

最后用 **RRF** 把两边的排名合并。这是本项目的技术骨架。

### 3.2 依赖关系图（谁 import 谁）

理解工程代码最快的方法，是先搞清楚"谁调用谁"。本项目是**严格单向**的：

```
                        ask.py  （入口，什么都 import）
                           │
        ┌──────────────────┼───────────────────┐
        ▼                  ▼                   ▼
    campus_rag/web.py  campus_rag/evaluate.py  sweep/bench/calibrate/demo_check
        │                  │                   │
        └──────────┬───────┴───────────────────┘
                   ▼
            campus_rag/engine.py   ← 核心：闸门 + 生成
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
  campus_rag/retriever.py   campus_rag/llm.py      ← llm 是可选分支
        │
        ├──▶ campus_rag/text.py    （分词）
        └──▶ campus_rag/data.py    （Chunk 数据类型）

  campus_rag/config.py  ← 被几乎所有文件 import（参数中心）
  campus_rag/qa_logger.py ← 旁路，谁都可以调，失败了也不影响主流程
```

**这张图有个关键含义**：`text.py` / `data.py` / `retriever.py` 这三层
**完全不需要网络、不需要 API key、不需要任何第三方库**。
它们只用 Python 标准库（`re`、`math`、`pathlib`、`json`）。
这就是 README 里"离线优先"的技术含义：**检索层没有任何外部依赖**。

## 第 4 章 · 一次提问的完整旅程（核心中的核心）

这一章是全书的**主心骨**。把这一章读透，剩下的章节都只是在给这里的某一步补细节。

### 4.1 全景流程图

```
  ① 你输入："南海校区宿舍晚上几点关门？周五周六和法定节假日会延后吗？"
       │
       ▼
  ② 检索（retriever.search）
       ├─ 分词：把问题切成 token（bigram + unigram + 英文词干）
       ├─ 通道 A：BM25 词法打分 → 排好序的 24 个候选块
       ├─ 通道 B：字符 3-gram TF-IDF 余弦 → 另一份 24 个候选块
       ├─ 通道 C（可选）：同义词扩展查询 → 再一份候选块（低权重 0.4）
       └─ RRF 融合三份排名 → 得到最终前 5 个块（ScoredChunk）
       │
       ▼
  ③ 置信度打分（engine._confidence）→ 一个 0~1 的数，本次是 0.5609
       │
       ▼
  ④ 闸门判断：0.5609 >= 0.42 ？ → 通过，继续
       │
       ├─── 不通过 ──▶ 【回答形态 C：拒答】直接返回"资料中没有相关内容"
       │
       ▼
  ⑤ 拼上下文：把前 4 个块按 [1][2][3][4] 编号拼成一段文字
       │
       ▼
  ⑥ 生成（两种可能）
       ├─ 有 LLM：发给大模型 + 接地提示词 → 【回答形态 A：LLM 生成】
       └─ 无 LLM / 调用失败：抽取式选句 → 【回答形态 B：抽取式降级】
       │
       ▼
  ⑦ 组装 Answer 对象（答案 + 置信度 + 来源 + 检索轨迹）→ 返回
       │
       ▼
  ⑧ 记一行日志到 data/logs/qa_日期.jsonl
```

### 4.2 同一次提问，三个环节的真实数据

**第 ② 步的产出**（检索排序结果）：

| 排名 | 来源文档 | 标题路径 | RRF 分数 | 片段开头 |
| --- | --- | --- | --- | --- |
| 1 | 08-校规校纪问答.md | … > 常见问题 | 0.0328 | **问：宿舍晚上几点关门？迟归怎么办？** 答：宿舍大门每日 6:00 开… |
| 2 | 08-校规校纪问答.md | … > 宿舍管理与生活秩序 > 门禁与作息 | 0.0323 | - 宿舍大门每日 **06:00** 开门；**周日至周四 23:00** 关门熄灯… |
| 3 | 09-通知公告问答.md | … > 医疗与医保报销 | 0.0317 | - **南海校园门诊报销时间**：每月**第四周周三**… |
| 4 | 09-通知公告问答.md | … > 常见问题 | 0.0312 | …禁带手机…**问：南海校区医保门诊报销怎么办理？** |

注意第 3、4 名是**完全无关**的内容。这印证了 2.2 节说的：排序算法永远会给你前 N 名。
同时注意第 1、2 名都相关，而第 1 名是个 FAQ 问句（**它是问题不是答案**）——
这就是为什么 `engine.py` 里要有"问句降权"（第 9 章会讲）。

**第 ③ 步的产出**（置信度分项信号，实跑打印）：

## 第 5 章 · config.py：所有旋钮集中放

### 5.1 它做了什么

```python
@dataclass
class Config:
    chunk_size: int = 480
    top_k: int = 4
    answer_threshold: float = 0.42
    ...
```

`@dataclass` 是 Python 的一个"语法糖"（装饰器）。
它帮你自动生成 `__init__`，所以你可以写 `Config(chunk_size=200)`，
而不用自己写十行 `self.chunk_size = chunk_size`。

**为什么要把参数集中在一个文件里？** 因为做实验的时候，
你需要"只改一个参数、其它全都不变"（这叫控制变量）。
如果阈值写死在 `engine.py` 第 286 行，你就没法让 `sweep.py` 一次跑 55 种组合。
集中之后，实验脚本只要 `Config(answer_threshold=th)` 就能造出一个新配置。

### 5.2 关键参数逐个解释

| 参数 | 默认值 | 它控制什么 | 调大会怎样 |
| --- | --- | --- | --- |
| `chunk_size` | 480 | 一个"块"最多多少字 | 块更大、内容更全，但关键词被稀释，召回下降 |
| `chunk_overlap` | 80 | 相邻块重叠多少字 | 防止答案正好被切在块边界上 |
| `min_chunk_len` | 40 | 小于这个长度的块并进上一块 | 避免产生大量碎片块污染检索 |
| `top_k` | 4 | 最终返回几个块 | 返回更多，但噪声也更多 |
| `candidate_k` | 24 | 每条通道先各取多少个候选再融合 | 越大越全，越慢 |
| `rrf_k` | 60 | RRF 公式里的平滑常数 | 见 8.5 节 |
| `max_context_chunks` | 4 | 送给大模型几块 | 太多会超出上下文、引入噪声 |
| `temperature` | 0.2 | 大模型随机性 | 越高越发散（对政策问答是坏事） |
| **`answer_threshold`** | **0.42** | **拒答闸门的及格线** | **越高越保守（拒答更多）** |
| `evidence_k` | 5 | 判断"有没有证据"时看几个块 | 越大越宽松（对多跳问题友好） |
| `rare_penalty` | 0.30 | 稀有词惩罚强度 | 越大越不信任"冷门词命中" |
| `rare_doc_ratio` | 0.12 | 多稀有算"稀有" | 见 9.4 节 |
| `eval_k` | 3 | 评测时算 Hit@几 | — |

**重点看 `answer_threshold` 和 `evidence_k` 的关系**（这是最容易被面试官追问的一点）：

- `top_k`（4）= **送给模型的块数**，要精；
- `evidence_k`（5）= **判断有没有证据的块数**，要宽。

为什么不合并成一个？因为这个场景真实存在：

> 问："申请推免要准备什么材料、什么时候交、科研怎么计分？"
> 答案分散在 3 个小节，融合排序后分别排在第 2、4、5 名。
> 如果你只看前 3 名（`top_k`）来判断"有没有证据"，你会**误判为证据不足而拒答**——
> 明明资料里有答案。所以判断证据时用更宽的 5 个块。

实测数据也支持这个设计（本文实跑，阈值 0.42 固定）：

| evidence_k | 拒答准确率 | 漏答率 | 硬答率 | 覆盖率 |
| --- | --- | --- | --- | --- |
| 1 | 54.5% | 62.5% | 0.0% | 37.5% |
| 2 | 68.2% | 43.8% | 0.0% | 56.2% |
| 3 | 68.2% | 43.8% | 0.0% | 56.2% |
| 4 | 68.2% | 43.8% | 0.0% | 56.2% |
| **5（默认）** | **77.3%** | **31.2%** | **0.0%** | **62.5%** |
| 6 | 81.8% | 25.0% | 0.0% | 65.6% |
| 8 | 81.8% | 25.0% | 0.0% | 65.6% |
| 10 | 86.4% | 18.8% | 0.0% | 71.9% |

有意思的地方来了：**`evidence_k=6` 和 `10` 的指标比默认的 5 更好**。
为什么默认值是 5 而不是 6？

因为**默认值是在更早的语料版本上标定的**，而这份 22 题评测集是**后来新建的**。
项目刻意**没有**用新评测集去重新调参——理由是（见 `docs/known-issues.md`）：
拿这套评测集去挑参数，它就"变成了训练集"，之后报出来的所有指标都不再是**样本外**的。
**这就是"我知道参数还能更好看，但我不这么干"。**

### 5.3 环境变量：`Config.from_env()`

```python
env_map = { "llm_api_key": ("CAMPUS_RAG_API_KEY", "DEEPSEEK_API_KEY", "OPENAI_API_KEY"), ... }

if not cfg.llm_api_key:        # ★ 没配 key 就别去调接口，直接走降级路径
    cfg.use_llm = False
if not cfg.embed_api_key:
    cfg.use_embeddings = False
```

`env_map` 的意思是"按顺序找这几个环境变量，谁先有值就用谁"，所以可以这样启动：

```powershell
$env:DEEPSEEK_API_KEY = "sk-xxxx"     # 只对当前窗口有效
python ask.py --web --llm
```

**为什么用环境变量而不写进配置文件？** 因为 API key 是密码——
写进 `config.py` 并 commit，就等于把它上传到 GitHub 了。
最后那两行是"永不报错"的第一层实现：没 key 就根本不发请求，用户不会看到一堆 401。

#### 优先级里唯一的例外：离线闸

默认规则是**函数参数 > 环境变量 > 默认值**。但有一个例外，而且是刻意留的：

```python
values.update({k: v for k, v in overrides.items() if v is not None})   # 参数覆盖环境变量
cfg = cls(**values)
if offline_requested():        # ★ 离线闸最后落，谁都不许把它翻回去
    cfg.use_llm = False
    cfg.use_embeddings = False
```

离线是"不许联网"的**安全闸**，不是普通配置项，所以它必须**最后**生效。
原先它写在 `overrides` 之前，结果 `CAMPUS_RAG_OFFLINE=1 ... --llm` 会被 `--llm` 翻掉，
而命令行 `--offline` 却能压住 `--llm`——同一个意图两种写法结果不同，
等于环境变量那一路是个**假开关**。

#### 一个容易踩的坑：key 设了 ≠ 启用了

| 你设的变量 | 要不要 `--llm` | 为什么 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | **要** | `build_engine` 里的自动启用只认下面那一个名字 |
| `CAMPUS_RAG_API_KEY` | 不要 | `use_llm=... or bool(os.environ.get("CAMPUS_RAG_API_KEY"))` |

（所以第 11 章讲 `build_engine` 时能看到那行**只认一个别名**的自动启用——
这不是 bug，但它意味着"设了 key 却还是离线抽取式"是**正常现象**，不是 key 坏了。
`python ask.py --info` 会明确告诉你：`↳ 已检测到 API key，但本次没启用：加 --llm 即用`。）

## 第 6 章 · text.py：中文怎么切才检索得到

这是全项目**最反直觉**、也最能体现"做过实验"的一个文件。请认真读完。

### 6.1 问题的起点：中文没有空格

英文里 `library` 是一个词，天然就能切。
中文的"图书馆闭馆前提前多久清场"是一串连续的汉字，
计算机不知道"图书馆"是一个词、"闭馆"是另一个词。

主流做法是**词典分词**（把句子和一本词典比对，切出词），
常用工具是 `jieba`。本项目**不用**它，理由写在文件开头：

> 面试现场环境不可控（可能没网、pip 装不上）。标准库方案 = 零风险。

那不用词典怎么办？用 **CJK bigram（二元组）**：把连续的汉字按"每两个相邻字"切。

```python
def bigrams(run: str) -> List[str]:
    return [run[i : i + 2] for i in range(len(run) - 1)]
```

```
"宿舍关门" -> ['宿舍', '舍关', '关门']
```

注意 `'舍关'` 是**跨词边界**造出来的假词。这不是 bug，是 bigram 的固有特性：
它用"多一些假词"换"不需要词典"。

### 6.2 单字（unigram）为什么必须补上

项目最初只用 bigram，结果撞上一个真实缺陷。代码注释里写得非常清楚：

> 文档里的双字词无法被单字或跨词查询匹配到。
> 例：语料写"奖励标准：8000 元"，用户问"金额是多少"——
> 两者没有任何一个共同的 bigram（"金额" 在文档里不存在），直接漏检。

所以最终实现是 **bigram 为主 + unigram（单字）为辅**：

```python
def cjk_tokens(run, unigrams=True):
    grams = [run[i : i + 2] for i in range(len(run) - 1)]
    if unigrams:
        grams.extend(run)     # ← 把所有单字也加进去
    return grams
```

实跑验证：

```python
>>> tokenize("南海校区宿舍晚上几点关门？")
['南海', '海校', '校区', '区宿', '宿舍', '舍晚', '晚上', '上几', '几点',
 '点关', '关门',
 '南', '海', '校', '区', '宿', '舍', '晚', '上', '几', '点', '关', '门']
#   └────────── bigram（11 个）──────────┘  └──── unigram（12 个）────┘
```

**面试可以这样解释为什么加单字不会污染排序**：
单字（"的""是""南"）在每篇文档里都出现，所以它的 IDF（见 8.3）**非常低**，
低到几乎不影响 BM25 的得分——它只起到"兜底召回"的作用。
而真正稀有的双字词（"推免""旷课"）IDF 很高，主导排序。

### 6.3 停用词：为什么要"按字"处理

```python
_STOP = {"的","了","是","在","和","与","或","及","也","都","而","被","把","对",
         "什么","怎么","怎样","如何","为什么","哪些","哪个","多少","吗","呢","啊", ...}
```

`tokenize()` 最后会把这些 token 扔掉：

```python
if drop_stopwords:
    tokens = [t for t in tokens if t not in _STOP and len(t) > 0]
```

关键细节：因为 bigram 会产生"金的""是的"这类噪声，
而中文停用词表按"字"收录，`'的'` 被丢掉之后，
包含它的 bigram（如 `'金的'`）依然存在——**这就是为什么置信度算法里还要额外做稀有词惩罚**（9.4 节）。

### 6.4 英文与数字：轻量词干 + 保留小数

```python
_LATIN_RE = re.compile(r"[a-z0-9]+(?:[.\-_][a-z0-9]+)*")
```

这条正则的意思是："字母数字连成串，中间允许出现 `.`、`-`、`_` 再跟字母数字"。
这样 `3.5`、`cet-4`、`fm75` 都会整体保留成**一个** token，不会被拆散。

英文还会做**极简词干化**（把 `-ing` `-s` `-ed` 这类后缀剥掉）：

```python
_SUFFIXES = ("ing", "ers", "er", "ies", "ed", "es", "s")

def _stem(word):
    if len(word) <= 4 or not word.isalpha():
        return word          # 太短的不动（避免把 "is" 变成 "i"）
    for suf in _SUFFIXES:
        if word.endswith(suf) and len(word) - len(suf) >= 3:
            base = word[: -len(suf)]
            if suf == "ies":
                base += "y"      # studies -> study
            return base
    return word
```

它能处理 `studies → study`、`reporting → report`，
但处理不了 `went → go`（那需要动词变形表）。**这是刻意的"够用就好"**——
中文语料里英文占比很小。

### 6.5 字符 3-gram：给向量通道准备的另一套切法

```python
def char_ngrams(text, n=3):
    s = re.sub(r"\s+", "", text.lower())     # 先把空格全去掉、变小写
    return [s[i : i + n] for i in range(len(s) - n + 1)]
```

```
char_ngrams("宿舍关门", 3) = ['宿舍关', '舍关门']
```

**注意它跟 bigram 是两套完全不同的切法**，用于**两个不同的通道**：

| | 切法 | 用在哪个通道 | 特点 |
| --- | --- | --- | --- |
| `tokenize()` | bigram + unigram（汉字）+ 词干（英文） | BM25 词法通道 | 有"词"的概念，IDF 有效 |
| `char_ngrams()` | 3 个连续字符，**忽略空格** | TF-IDF 向量通道 | 完全不关心词边界，纯字面重叠 |

为什么要两套不同切法？因为**"互补"才有融合的价值**。
如果两条通道用的是同一种切法，它们会给出几乎一样的排序，融合就没意义了。

## 第 7 章 · data.py：把 Markdown 变成"块"

### 7.1 为什么必须切块

整篇 291 行的文档当一个单位 → 一旦命中就要把 291 行全送给模型（超上下文，90% 是噪声）。
按行切 → "06:00 开门"和"23:00 关门"被切成两条，问"几点关门"只能命中半句。

切块的目标：**每块语义完整、又能被单独引用**。经验值中文 300~600 字/块（本项目 480）。

### 7.2 切块三步走

**第一步：按 Markdown 标题切"语义块"**

```python
_HEADING_RE = re.compile(r"^(#{1,6})\s+(.*)$")     # 匹配 "## 宿舍管理"
```

`##` 的数量代表层级，所以代码维护一个 `heading_stack`（标题栈）：

```python
m = _HEADING_RE.match(raw.strip())
if m:                                    # 这行是标题
    flush()                              # 先把攒着的正文存成一个块
    level = len(m.group(1))              # "##" -> 2
    heading_stack = heading_stack[: level - 1]   # 砍掉比它深的层级
    while len(heading_stack) < level - 1:
        heading_stack.append("")          # 补齐空位
    heading_stack.append(m.group(2).strip())
else:
    buf.append(raw)                       # 普通正文行先攒着
```

效果是每块都带一条**标题路径**：`手册 > 宿舍管理与生活秩序 > 门禁与作息（南海校园）`。
两个用途：① **展示**（UI 显示"哪个文件·哪一节"，学生能对着找）；
② **打分**（标题命中是强信号——问"门禁"时，标题里有"门禁"的块显然更相关；
这个加成通过"把标题词重复计入词频"实现，见 8.4 节）。

**第二步：块太大就按句子切，并保留 overlap**

```python
for s in sents:
    if len(buf) + len(s) <= max_len:      # ① 还装得下，继续攒
        buf += s
        continue
    if buf.strip():                        # ② 装不下了，先把攒的存成一个块
        out.append(buf.strip())
    tail = buf[-overlap:] if overlap > 0 and buf else ""   # ③ 取上一块的尾巴
    buf = (tail + s) if len(s) < max_len else ""
    if len(s) >= max_len:                  # ④ 单句就超长，只好硬切
        step = max(1, max_len - overlap)
        out.extend(s[i : i + max_len].strip() for i in range(0, len(s), step))
```

句子边界正则 `_SENT_SPLIT_RE = re.compile(r"(?<=[。！？!?；;])\s*|\n{2,}")`，
其中 `(?<=...)` 是"向后看"断言，所以它在"。"之后断开但**不会把"。"本身吃掉**。

实跑（`max_len=40, overlap=10`）：


没有重叠，"清场"在块 B、问题里的"提前多久"在块 A，两边都不完整。

**实跑发现的一处注释与实现不一致**：docstring 说"超长时带 overlap 滑窗"，
但动作 ④ 那个分支**只在"单句本身长于 max_len"时才触发**。实跑真实语料：


它不是 bug：真正起作用的是动作 ③ 的**句子级重叠**；若哪天丢进一篇没有句号的长文本，④ 会兜住它。

### 8.2 通道 A：手写 BM25

**BM25** 是信息检索几十年来的经典排序公式（Elasticsearch / Lucene 的默认算法）。
不用背推导，只要知道它解决三个问题：

| 问题 | BM25 的处理 |
| --- | --- |
| 词越常见越不值钱（"的"到处都是） | 乘 IDF：`log(1 + (N - df + 0.5)/(df + 0.5))` |
| 一个词出现 10 次 ≠ 相关 10 倍 | 词频饱和项：`f*(k1+1) / (f + k1*(...))` |
| 长文档天然更容易命中词，不该占便宜 | 长度归一化：`b * len/avg_len` |

```python
class BM25:
    def __init__(self, chunks, k1=1.2, b=0.75):     # k1/b 是 Lucene 的默认值
        for i, ch in enumerate(self.chunks):
            counts = token_counts(ch.text)
            for tok, c in token_counts(ch.heading).items():
                counts[tok] = counts.get(tok, 0) + 2 * c     # ★ 字段加权：标题词词频 ×3
            for tok, c in token_counts(ch.title).items():
                counts[tok] = counts.get(tok, 0) + c         # 文档标题 ×2
            self.tf.append(counts)
            for tok in counts:
                self.df[tok] = self.df.get(tok, 0) + 1              # 文档频率
                self.postings.setdefault(tok, []).append(i)         # 倒排索引
        self.idf = {tok: math.log(1 + (n - df + 0.5) / (df + 0.5))
                    for tok, df in self.df.items()}
```

**倒排索引**（`postings`）是搜索引擎的核心结构：`"旷课" -> [块12, 块14]`。
有了它，搜索时不用遍历全部 63 个块，而是直接拿这两个下标去算分。
本项目语料小（63 块），暴力遍历也毫秒级，但结构上是按十万级规模设计的。

**字段加权的实现很廉价**：不另算一套公式，只是把标题词词频人为放大（`+= 2*c`），
效果就是标题命中比正文命中权重高约 3 倍。

```python
def search(self, query, top_k=5):
    scores = {}
    for tok in tokenize(query):
        posting = self.postings.get(tok)      # 哪些块包含这个词
        if not posting: continue
        idf = self.idf.get(tok, 0.0)
        for i in posting:
            f = self.tf[i][tok]               # 这个词在这个块里出现几次
            denom = f + self.k1 * (1 - self.b + self.b * self.len[i] / self.avg_len)
            scores[i] = scores.get(i, 0.0) + idf * f * (self.k1 + 1) / denom
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)[:top_k]
```

### 8.3 通道 B：字符 3-gram TF-IDF + 余弦相似度

一句话：**把每个块表示成高维稀疏向量，比较两个向量的夹角。**

```python
class TfidfVector:
    def __init__(self, chunks, n=3):
        docs = [char_ngrams(ch.text + " " + ch.heading, n) for ch in self.chunks]
        for grams in docs:
            for g in set(grams):
                self.df[g] = self.df.get(g, 0) + 1        # 每个 gram 出现在几个块里
        for grams in docs:
            vec = {}
            for g, c in {...}.items():                    # g→出现次数
                idf = math.log((n_docs + 1) / (self.df.get(g, 0) + 1)) + 1.0
                vec[g] = (1 + math.log(c)) * idf
            self.vectors.append(_l2_normalize(vec))
```

三个公式细节（都是 sklearn 的通行做法）：`(1 + log(c))` 是**次线性词频**（出现 10 次不代表重要 10 倍）；
`log((N+1)/(df+1)) + 1` 是**平滑 IDF**（避免除零，且最小值是 1 不会变负）；
`_l2_normalize` 让向量长度为 1，于是**余弦相似度退化成点积**，省掉每次算模长的开销。

查询时的打分：

```python
def search(self, query, top_k=5):
    q_tf = {}
    for g in char_ngrams(query, self.n):
        q_tf[g] = q_tf.get(g, 0) + 1
    ...  # 同样的 tf-idf 加权 + 归一化
    for i, vec in enumerate(self.vectors):
        small, big = (q_vec, vec) if len(q_vec) <= len(vec) else (vec, q_vec)
        dot = sum(w * big.get(g, 0.0) for g, w in small.items())   # 稀疏点积：遍历短的那边
        if dot > 0:
            scores.append((i, dot))
```

`small, big = ...` 这一行是**稀疏向量的性能优化**：
两个向量里绝大多数维度都是 0，遍历"非零项少"的那一个就够了。

**这条通道为什么能救"改写"问题？**

问："最多能借几本书？"，文档写"可借册数 15 册"。
两条通道的 bigram 交集可能是空的。但字符 3-gram 会命中 `"能借"`? 未必……
真正起作用的是**单字 unigram 通道**（`"借"` 命中 `"可借"`）。
字符 3-gram 主要救的是**顺序不同/多字少字**的情况，比如
问 `"提前多久清场"`、文档 `"结束前提前 10 分钟清场"` 会共享 `"前提前"`? ——
实际共享的是 `"提前"`/`"清场"` 这些 bigram。**两条通道的互补性主要体现在排序差异上**。

### 8.5 RRF：只用排名，不用分数

**这是本章最重要的一个设计决策。**

问题：BM25 的分数可能是 65.88，TF-IDF 余弦是 0.0889，embedding 余弦是 0.83。
**它们的量纲完全不同，怎么加权求和？** 65.88 乘 0.5 加 0.0889 乘 0.5 —— 毫无意义。

RRF（Reciprocal Rank Fusion）的解法是：**根本不用分数，只用排名。**

```python
def rrf_fuse(rankings, k=60, weights=None):
    """RRF：score = Σ w / (k + rank)。"""
    fused = {}
    for ranking, w in zip(rankings, weights):
        for rank, (idx, _score) in enumerate(ranking, start=1):
            fused[idx] = fused.get(idx, 0.0) + w / (k + rank)
    return sorted(fused.items(), key=lambda kv: kv[1], reverse=True)
```

翻译成人话：

- 在**任何一条通道里排第 1**，得 `1/(60+1) = 0.0164` 分；
- 排第 2 得 `1/62 = 0.0161`；
- 排第 10 得 `1/70 = 0.0143`。

每个块把所有通道给它的分数加起来，总分高的排前面。

**为什么除以 `(k + rank)` 而不是直接用 `1/rank`？**
因为 `1/1 = 1`、`1/2 = 0.5` —— 第 1 名和第 2 名的差距太大，
一条通道的第 1 名会碾压其它通道的所有结果。加上 `k=60` 后，
第 1 名和第 2 名只差 0.0003，**多条通道的共识变得更重要**：
一个块如果在三条通道里都排第 5，它会比"只在一条通道里排第 1"的块得分更高。
这正是我们想要的——**共识优于极端**。

看 4.2 节的实际数据：第 1 名 0.0328、第 2 名 0.0323，差距极小。
这不是 bug，是 RRF 的特性。所以 `engine.py` 里的置信度**不能只看 RRF 分数**
（因为 RRF 分数没有绝对意义，只反映"排名共识"）——这就是下一章要讲的。

### 8.7 覆盖率加成与片段抽取

检索函数最后一步：


`_coverage` = 查询词有多少比例出现在这个块里。
乘一个 `1 + 0.25*覆盖率` 的意思是：**"回答得越全面"的块应该排更前**。

防的是这种情况：一篇很长的文档，因为词多，BM25 分数天然高，

```python
def answer(self, question, top_k=None):
    top_k = top_k or self.cfg.top_k

    # ① 检索（注意取了 max(top_k, evidence_k) = max(4,5) = 5 个）
    results = self.retriever.search(question, top_k=max(top_k, self.cfg.evidence_k))

    # ② 算置信度
    confidence, conf_signals = self._confidence(question, results)

    # ③ 整理引用来源（只给前 max_context_chunks=4 个）
    sources = [ {...} for i, r in enumerate(results[:self.cfg.max_context_chunks], start=1) ]

    # ④ 组装"检索轨迹"（给 UI 和调试看的透明信息）
    trace = {...}
    trace.update(conf_signals)

    # ⑤ 防线 1：闸门
    if confidence < self.cfg.answer_threshold or not results:
        return Answer(mode="refusal", ...)         # 直接返回拒答

    # ⑥ 拼上下文
    ctx_chunks = results[:self.cfg.max_context_chunks]
    context = "\n\n".join(f"[{i}] 来源：{r.chunk.source} · {r.chunk.heading}\n{r.chunk.text}" ...)

    # ⑦ 防线 2/3：LLM 生成，失败即降级
    if self.llm is not None and self.cfg.use_llm:
        try:
            res = self.llm.chat(SYSTEM_PROMPT, USER_TEMPLATE.format(context=context, question=question))
            if res.text:
                return Answer(mode="llm", ...)
            err = "LLM 返回空内容"
        except LLMError as e:
            err = str(e)
        return Answer(answer=self._extractive(question, ctx_chunks), mode="extractive", error=err, ...)

    # ⑧ 没有 LLM 时
    return Answer(answer=self._extractive(question, ctx_chunks), mode="extractive", ...)
```

**Python 语法小提示**：`results[:5]` 是**切片**；`enumerate(list, start=1)` 同时给"下标"和"元素"
（从 1 开始是因为引用编号 `[1]` 更符合直觉）；`f"[{i}]..."` 是 **f-string**。

**`Answer` 对象**是这一层的输出契约：

```python
@dataclass
class Answer:
    question: str
    answer: str          # 答案文本
    mode: str            # ★ 三选一："llm" | "extractive" | "refusal"
    confidence: float    # 0~1
    sources: List[dict]  # 引用来源（含原文，可展开核对）
    retrieved: List[dict]# 所有检索结果（评测用）
    latency_ms: int
    error: Optional[str] # 降级原因（有值时说明降级了）
    trace: dict          # 检索轨迹（透明度）
```

`mode` 是全系统的"状态标签"：UI 用它显示不同颜色徽章，评测用它判断"该答的答了吗"。
**注意 `refusal` 是一个正常的 mode，不是异常。**

### 9.2 置信度：三个信号 + 两个校准项

全项目最难的 65 行。先看它的框架：

```python
n_evidence = max(1, self.cfg.evidence_k)
top_indexes = [self.retriever.chunks.index(r.chunk) for r in results[:n_evidence]]
total_idf, oov = bm25.idf_mass(q_tokens)                      # 查询总信息量 & 缺失部分
idf_cov_raw = bm25.weighted_coverage_union(q_tokens, top_indexes)
rare_share = _rare_idf_share(bm25, q_tokens, len(self.chunks), self.cfg)
idf_cov = idf_cov_raw * (1.0 - self.cfg.rare_penalty * rare_share)   # 先打稀有词折扣
```

**信号 1：`idf_cov` —— IDF 加权联合覆盖率（主信号，权重 0.52）**

朴素覆盖率（错误做法）是 `命中词数 / 查询词总数`。问题：问"什么是什么"命中一堆虚词，
覆盖率能到 100%，**然后系统就以为自己很有把握，开始硬答**。正确做法是按信息量加权：

```python
def weighted_coverage_union(self, query_tokens, doc_indexes):
    total, _ = self.idf_mass(q)              # 分母：查询的总信息量
    covered = {}
    for idx in doc_indexes:                  # 分子：被这 N 个块覆盖的信息量
        for tok, count in self.tf[idx].items():
            if count and tok in q:
                covered[tok] = True
    hit = sum(self.idf.get(t, 2.0) for t in covered)
    return min(1.0, hit / total)
```

直觉：`"宿舍"` 很稀有 → IDF 高 → 命中它加很多分；`"的"` 到处都是 → IDF 极低 → 几乎不加分。
所以它衡量的是**"这个问题的信息量有多少被证据块接住了"**，而不是"字面撞上了几个词"。

注意"**联合**"（union）：`doc_indexes` 是前 5 名**一组**块，只要查询词在**任何一个**块里出现就算覆盖。
这是为了多跳问题——证据分散在多个块里，只看第 1 块会误判。

**分母为什么要包含"语料里根本不存在的词"？**

```python
for t in set(tokens):
    total += self.idf[t] if t in self.idf else 2.0     # 不存在的按"高价值但缺失"计
    if t not in self.idf:
        oov += 2.0
```

问"退相干时间是多少"而语料从没有"退相干"时，这个缺失的重要概念**应该拉低覆盖率**。
不计入分母，覆盖率就虚高了。所以按 2.0 的虚拟信息量计入分母，但**同时计入 oov**，交给 OOV 惩罚统一处理。

**信号 2：`focus` —— 第 1 名领先第 2 名多少（权重 0.10）**

```python
spread = max(0.0, (results[0].score - results[1].score) / results[0].score)
focus = min(1.0, spread / 0.20)
```

第 1 名和第 2 名几乎打平（`spread ≈ 0`）= **多篇文档都沾边，但没有一篇是真的在回答**，
这正是"问题超出语料范围"的典型症状。实跑：正常回答 `spread=0.0161`、拒答 `0.0082`——
区分度有限（RRF 分数本来就挤在一起），所以权重只给 0.10，属**辅助信号**。

**信号 3：`lex` —— BM25 分数的饱和压缩（权重 0.38）**

```python
lex = lexical_top / (lexical_top + 14.0) if lexical_top > 0 else 0.0
```

BM25 原始分无上界（实跑见过 5 / 17 / 47 / 65），用 `x/(x+14)` 压进 0~1：

| BM25 分 | 5 | 17 | 47 | 65 | ∞ |
| --- | --- | --- | --- | --- | --- |
| 压缩后 | 0.26 | 0.55 | 0.77 | 0.82 | →1.0 |

**为什么不用"除以最大值"？** 注释说得直白：**有下限才有区分度**——u01 的 5.9 与 q13 的 32.6 必须分开。
`14.0` 是"半饱和点"（分数到 14 时压缩值 0.5）。⚠️ **这个 14 是手调常数、没有 extract 到 config**，
是个已知小瑕疵；要改它请重跑评测。

**合成**：`base = 0.52 * idf_cov + 0.10 * focus + 0.38 * lex`（权重和 = 1.00，
设计意图：主信号占一半、BM25 绝对分近四成、打平信号只占一成）。

### 9.3 校准项 1：OOV 惩罚

```python
if total_idf > 0:
    oov_share = min(1.0, oov / total_idf)
    base *= 1.0 - 0.85 * oov_share
```

`oov` = Out-Of-Vocabulary，指**查询里语料从未出现过的词**所占的信息量。

翻译：**你问的十成概念里，如果有三成我压根没见过，我的信心就打掉 25.5%**（`0.85 × 0.3`）。

看 4.3 节的游泳池例子：`oov_share = 0.3518` → `base *= 1 - 0.85×0.3518 = 0.701`，
置信度从 0.42 左右被打到 0.296 → **拒答成立**。

| 问题 | OOV 情况 | 结果 |
| --- | --- | --- |
| "最多能借几本书？"（文档写"可借册数"） | OOV 低（"借""书"都在语料里） | 该答 |
| "退相干时间是多少？" | OOV 高（"退相干"从未出现） | 该拒答 |

注释对它的定位很准：**这是区分"用词不同"（正常，能答）与"概念不存在"（该拒答）的唯一非词法依据。**

### 9.4 校准项 2：稀有词惩罚

**这个陷阱非常反直觉。** IDF 的定义是"越稀有 IDF 越高"，于是语料里只出现 1 次的词 IDF **非常高**。
用户问题里恰好有这么一个词、某个块又碰巧包含它 → 覆盖率被**抬得很高**，但这是**巧合，不是证据**。

真实案例（注释里写的）："水温""麻辣香锅"这类词只出现一次。问"实验室水温要求多少度"，
命中"水温"这一个稀有词，覆盖率被抬高 → **硬答**。

修法：把"查询信息量落在极稀有词上的比例"当作惩罚项。

```python
def _rare_idf_share(bm25, q_tokens, n_docs, cfg):
    threshold = max(cfg.rare_doc_min, int(cfg.rare_doc_ratio * n_docs))   # max(2, 63*0.12) = 7
    total, _ = bm25.idf_mass(q_tokens)
    rare = sum(bm25.idf.get(t, 2.0)
               for t in q_tokens
               if 0 < len(bm25.postings.get(t, ())) <= threshold)          # 出现 ≤7 次算稀有
    return min(1.0, rare / total)

idf_cov = idf_cov_raw * (1.0 - self.cfg.rare_penalty * rare_share)         # 惩罚在这里生效
```

实跑数据：

| 问题 | idf_coverage 原始 | rare_idf_share | 惩罚后 | 最终置信度 |
| --- | --- | --- | --- | --- |
| 宿舍几点关门 | 0.8100 | 0.5837 | **0.6682** | 0.5609 ✅ 作答 |
| 旷课多少节被警告 | 0.9539 | 0.6570 | **0.7659** | 0.6796 ✅ 作答 |
| 游泳池开放时间 | 0.4681 | 0.4669 | **0.4025** | 0.2960 ❌ 拒答 |

**注意第二行**：`rare_idf_share` 高达 0.657（最"可疑"）却仍然答对——
因为原始覆盖率 0.9539 实在太高，打完折还有 0.7659，加上 `lex` 也强（0.7717）。
**惩罚项不是一票否决，而是"打折"，设计得很克制。**

### 9.5 第三种回答形态：抽取式降级 `_extractive()`

这是"没有 LLM 时的答案"。核心思想：

> **绝不改写。从原文里挑最相关的句子原样抄出来，标上来源。**

因为它一个字的原文都不改，所以**它不可能产生幻觉**——这是它的全部价值。

#### 9.5.1 选哪些块

`extractive_chunks` 是个**类属性**（`RagEngine.extractive_chunks = 3`，写死不是 config 字段），
默认只从**前 3 个块**里挑句子。为什么不是 5 个、8 个？因为实测（本文实跑，端到端口径）：

| extractive_chunks | 1 | 2 | **3（默认）** | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- |
| 关键事实覆盖率 | 46.9% | 53.1% | **62.5%** | 62.5% | 62.5% | 62.5% |

`3` 之后**不再提升**——排名 4 以后的块里混进了"说得对但没回答这个问题"的句子。

> README 记录了一次更戏剧性的实验（用的是**修 bug 之前**的旧口径）：
> 凭直觉把候选块放宽到 5，覆盖率反而从 79.3% 掉到 69.0%。
> 修好口径后重跑，结论仍然成立（**3 块是拐点**），但"放宽到 4-6 块会更差"在当前语料上**已不复现**。

**"看起来更周到"的改动，必须让指标说话。**

#### 9.5.2 句子怎么打分

```python
def sentence_score(sent):
    toks = set(tokenize(sent))
    hits = effective_q & toks               # 命中的查询词
    if not hits:
        return 0.0
    score = 0.0
    for t in hits:
        score += bm25.idf.get(t, 2.0)       # ① IDF 加权
    score *= (bm25.k1 + 1.0) / (1.0 + bm25.k1 * (1.0 - bm25.b))    # ② 复用 BM25 的饱和/长度项
    score += 0.05 * len(re.findall(r"\d+(?:\.\d+)?%?", sent))      # ③ 数字是强答案信号
    score += 0.35 * len(key_terms & toks)                          # ④ 命中关键术语额外奖励
    return score / total_idf
```

- **③ 数字加权**：政策类问答的答案往往就是一个数字（"8000 元""30 天"），选句时优先带上数字。
- **② 复用 BM25**：这是 v3 迭代的关键一步——**从"手调乘子"改成"复用信息检索里已验证几十年的公式"**（词频饱和 + 句长归一化），而不是自己发明 `命中词数/句子长度` 再手调系数。

#### 9.5.3 三层加权：标题、主题短语、问句降权

```python
heading_text = r.chunk.heading + " " + r.chunk.title
topic_chars = max((len(p) for p in query_phrases[:8] if len(p) >= 3 and p in heading_text), default=0)
heading_bonus = 1.0 + min(0.9, 0.15 * topic_chars)      # 按匹配长度给分
```

**必须按匹配长度给分，不能"沾到就满分"**：
"国家奖学金"节匹配 4 字、"国家励志奖学金"节只沾到"奖学金"3 字，前者必须得分更多，
否则会把别的奖学金条目排到答案前面。这就是 `_topic_phrases()` 存在的理由——
它把查询滑窗切成主题短语，让"国家奖学金"能被完整匹配：

```python
_topic_phrases("国家奖学金的金额是多少")
# -> ['国家奖学金', '国家奖学', '家奖学金', '家奖学', '奖学金', '金额是', '国家奖', '学金', '家奖', '金额']
```

**问句降权 ×0.2**：`_is_question_like()` 判断一句话是"提问"还是"陈述"。

```python
_is_question_like("问：宿舍晚上几点关门？")   # True（以？结尾 / 以"问："开头）
_is_question_like("宿舍可以养宠物吗")         # True（以"吗"结尾且≤60字）
_is_question_like("答：宿舍大门每日 6:00 开。")  # False
```

原因：FAQ 文档里的问句和用户的问题**字面几乎一模一样**，token 命中数会碾压真正的答案句。

> 实测：问"挂科重修还能申请推免吗"，排第一的是文档里那句一模一样的问句，
> 靠"字面像"拿到 21 个 token 命中，把真正的答案句挤到后面。

**"相似度高"不等于"回答了问题"。**

#### 9.5.4 句子切分：为什么不能简单按换行切

```python
is_new_item   = bool(re.match(r"^(?:[#>*\-+]|\d+[.、)]|表[格头]|【)", line))
ends_sentence = bool(re.search(r"[。！？!?；;：:]$", line))
if merged and not is_new_item and (not ends_sentence or merged[-1].endswith(("：", ":"))):
    merged[-1] = (merged[-1] + line).strip()      # 并回上一行
```

要合并的两种情况：① **本行没写完**（不以句末标点结尾，常见于被换行折断的长句）；
② **上一行是纯标签**（以冒号结尾，如 `"答："`）。

不合并的后果：`"答：不能。"` 这种 4 字结论句会被切成 `"答："` + `"不能。"`，
前一段又被长度过滤丢掉，用户就看到一个莫名其妙的答案。

实测效果（注意第二句没合上，见下面的小缺陷）：

```
输入: - 核心条件：…均位于专业前 10%，
        且无不及格课程；须有至少一项突出表现
输出: 句: - 核心条件：…均位于专业前 10%，且无不及格课程；
      句: 须有至少一项突出表现      ← 咦，没合上
```

**暴露了一个真实小缺陷**：`ends_sentence` 把 `"；"` 也算作"句子结束"，
所以以 `"；"` 结尾那行的**下一行没有被合并**。它只影响长句完整性、不影响正确性
（两段都还在，只是分了家）。**说清这类小毛病，比假装完美更有说服力。**

#### 9.5.5 全局排序与摘录预算

```python
candidates.sort(key=lambda t: t[0], reverse=True)     # 全局排序，不是"每块取前2句"
for _score, i, s in candidates[:budget]:              # budget = 6 句
    lines.append(f"[{i}] {s}")
```

- **全局排序**：注释里的实测案例——"挑战杯奖金"这类问题，按块取句会把无关的奖项列表摘进来；
- **预算 6 句**：避免答案变成"整篇复制"。

### 9.6 三种回答形态对照表

| | LLM 生成 | 抽取式降级 | 拒答 |
| --- | --- | --- | --- |
| `mode` | `llm` | `extractive` | `refusal` |
| 触发条件 | 闸门通过 + 有 key + 调用成功 | 闸门通过 + 没 key / 调用失败 | 置信度 < 0.42 |
| 会不会改写 | 会（组织语言） | **绝不** | — |
| 会不会幻觉 | 理论可能，靠提示词约束 | **不可能** | — |
| 答案通顺度 | 好 | 一般（原文拼接） | — |
| 能不能核对 | 靠 `[n]` 引用 | 靠 `[n]` 引用 | 列出候选片段 |
| 定位 | **产品形态** | **保证永不白屏的兜底** | **正确行为** |

**最值得记住的一行**：`--llm` 是产品形态，离线抽取是兜底。
所以"离线优先"不是"功能阉割"，而是**把不确定性隔离在边界之外**。

### 9.7 系统的三道防线

`engine.py` 文件头的三句话就是全项目的防御哲学：

```
1. 闸门（gate）：检索置信度不足 → 直接拒答，不送给 LLM 编。
2. 接地提示词（grounded prompt）：只允许用材料说话，必须给出 [n] 引用。
3. 抽取式降级：LLM 不可用时，用"原文摘录 + 覆盖度打分"给一个可验证的答案。
```

`SYSTEM_PROMPT` 的六条规则里，**第 4 条尤其重要**：
"如果【资料】完全不支持该问题，直接回答'资料中没有相关内容'"——
它在**提示词层面又做了一次拒答**。所以就算闸门放行了（置信度 0.45），
模型看了资料后仍有机会说"资料中没有相关内容"——**两道独立的拒答机制**。

`CONTEXT.md` 对提示词的定位很精妙：**它防的是模型"知道但不该说"，不是模型不知道。**

## 第 10 章 · llm.py：那个"允许失败"的薄层

### 10.1 客户端代码本身很朴素

```python
def _post_json(url, payload, api_key, timeout):
    data = json.dumps(payload, ensure_ascii=False).encode("utf-8")
    req = urllib.request.Request(
        url, data=data, method="POST",
        headers={"Content-Type": "application/json",
                 "Authorization": f"Bearer {api_key}",
                 "Accept": "application/json"},
    )
    with urllib.request.urlopen(req, timeout=timeout) as resp:
        body = resp.read().decode("utf-8", errors="replace")
```

**`urllib` 是 Python 标准库里的 HTTP 客户端。** 用它而不是 `requests`，
是因为 `requests` 需要 `pip install`——违反"零依赖"原则。

`Authorization: Bearer sk-xxxx` 是 OpenAI 兼容接口的鉴权方式，
DeepSeek、硅基流动、通义都遵循这个协议，所以这套客户端能通用。

### 10.2 错误分类：让每种失败都有名字

```python
except urllib.error.HTTPError as e:
    detail = e.read().decode("utf-8", errors="replace")[:400]
    hint = {401: "API key 无效", 402: "余额不足", 429: "触发限流"}.get(e.code, "请求失败")
    raise LLMError(f"HTTP {e.code}（{hint}）: {detail}") from e
except urllib.error.URLError as e:
    raise LLMError(f"网络不可用: {e.reason}") from e
except TimeoutError as e:
    raise LLMError("请求超时") from e
```

**为什么要分类？** 因为不同的失败需要不同的动作：

| 错误 | 意思 | 你该做什么 |
| --- | --- | --- |
| 401 | key 错了 | 去检查环境变量 |
| 402 | 余额不足 | 充值 |
| 429 | 请求太快 | 等一下重试 |
| URLError | 没网 | 无所谓，会降级 |
| TimeoutError | 超时 | 无所谓，会降级 |

`raise ... from e` 是 Python 的**异常链**语法：
它把原始异常保存在 `__cause__` 里，这样报错信息里会同时显示两层原因，便于排查。

### 10.3 时间测量

```python
started = time.time()
data = _post_json(...)
latency = int((time.time() - started) * 1000)
```

`time.time()` 返回浮点秒数，相减得到耗时，乘 1000 变毫秒。
`int()` 取整。这是最朴素的计时方式（更精确的方式是 `time.perf_counter()`）。

### 10.4 响应解析

```python
try:
    choice = data["choices"][0]
    text = (choice.get("message") or {}).get("content") or ""
except (KeyError, IndexError, TypeError) as e:
    raise LLMError(f"返回结构异常: ...") from e
```

OpenAI 协议的标准响应结构：

```json
{
  "id": "...",
  "model": "deepseek-flash",
  "choices": [
    {"index": 0, "message": {"role": "assistant", "content": "宿舍大门…"}, "finish_reason": "stop"}
  ],
  "usage": {"prompt_tokens": 2013, "completion_tokens": 287, "total_tokens": 2300}
}
```

注意 `(choice.get("message") or {}).get("content")` 这个写法：
如果 `message` 是 `None`，`or {}` 会把它换成空字典，避免 `None.get()` 报错。
**这是一种防御式写法**，虽然啰嗦但不会崩。

`usage` 字段被保存下来，用于估算成本（README 里算了"单次问答约 0.003 元"）。

### 10.5 EmbeddingClient：可选通道

```python
def _embed(self, texts):
    out = []
    for i in range(0, len(texts), self.batch):        # 每次发 batch=16 条
        batch = texts[i : i + self.batch]
        data = _post_json(f"{self.base_url}/embeddings",
                          {"model": self.model, "input": batch}, ...)
        items = sorted(data.get("data", []), key=lambda d: d.get("index", 0))
        out.extend([item.get("embedding", []) for item in items])
    return out
```

`for i in range(0, len(texts), 16)` 是 Python 里"分块遍历"的标准写法：
`range(start, stop, step)` 生成 0, 16, 32, ...

`sorted(..., key=lambda d: d.get("index", 0))` 是个**重要的防御**：
有些服务返回的顺序不保证和请求一致，必须按 `index` 重排，
否则第 3 个块的向量会被安到第 7 个块上——**静默的错误结果，最难查**。

### 10.6 这一层的设计哲学

文件头写得很清楚：

> 关键工程决策：**LLM 是可选的、可失败的**。
> 它只负责"把检索结果组织成通顺的中文"，检索层完全不依赖它。
> 把不确定性隔离在一层薄薄的、可降级的边界内。

**"薄层"在这里是个技术判断**：

- 它只有 151 行，没有重试逻辑、没有连接池、没有流式输出；
- 它不缓存、不并发、不批量优化；
- 它唯一的职责是"发一个请求，拿回文本，出错就抛 `LLMError`"。

**为什么这么设计？** 因为不确定性已经被隔离在这一层了。
上层的 `engine.py` 只需要写一个 `try/except LLMError`，
整个系统就获得了"永不崩溃"的性质。**薄层 = 容易验证 = 容易替换。**

### 11.3 Windows 中文控制台坑

```python
def _use_utf8_console():
```

### 11.4 组装引擎 `build_engine()`

```python
def build_engine(args):
    cfg = Config.from_env(
        corpus_dir=args.corpus,

        answer_threshold=args.threshold,      # 命令行参数覆盖默认值
        evidence_k=args.evidence_k,
        use_llm=getattr(args, "llm", False) or bool(os.environ.get("CAMPUS_RAG_API_KEY")),
        ...
    )
    chunks = load_corpus(cfg.corpus_dir, max_len=cfg.chunk_size, overlap=cfg.chunk_overlap)
    if not chunks:
        raise SystemExit(f"语料为空：{cfg.corpus_dir}。请放入 .md/.txt 文件。")

    llm = LLMClient(cfg.llm_base_url, cfg.llm_api_key, cfg.llm_model, cfg.llm_timeout) if cfg.use_llm else None
    embedder = EmbeddingClient(...) if cfg.use_embeddings else None

    t0 = time.time()
    engine = RagEngine(chunks, config=cfg, llm=llm, embedder=embedder)

```

这 30 行就是**依赖注入**：

- **先建配置**（所有参数）；
- **再建数据**（`chunks`，从磁盘读）；
- **再建可选客户端**（没有 key 就是 `None`，**不是报错**）；
- **最后建引擎**，把前三样塞进去。

`raise SystemExit("消息")` 是"打印消息并退出"，退出码是 1。
比 `print()` + `exit()` 更规范。

`engine.build_ms = ...` 这一行是**动态加属性**——
Python 允许你往任何对象上挂新属性（`RagEngine` 类里并没有定义 `build_ms`）。
注释里加了 `# type: ignore[attr-defined]` 告诉类型检查器"我知道我在干啥"。
这是个实用小技巧：**不必为了记一个统计值去改类定义**。

### 11.5 参数解析 `argparse`

```python
p = argparse.ArgumentParser(prog="ask.py", description="...")
p.add_argument("question", nargs="?", default=None, help="要提问的问题；不填则进入交互模式")

```

`argparse` 是标准库的命令行解析器。几个要点：

- `nargs="?"`：这个位置参数**可以不给**（不给就进交互模式）；
- `action="store_true"`：加了 `--web` 就是 `True`，不加就是 `False`；
- `type=float`：自动把字符串 `"0.42"` 转成浮点数 `0.42`；
- `help="..."`：会出现在 `python ask.py --help` 里。

**注意 `--threshold` 的默认值和 `config.py` 里的默认值重复了**（都是 0.42）。
这是一个**小的一致性风险**：如果你改了一处忘了另一处，
命令行不带 `--threshold` 时用的是 argparse 的默认值，
而 `Config.from_env(answer_threshold=args.threshold)` 会**覆盖** config 里的值。
所以改阈值要**同时改两个地方**（或者干脆命令行传）。这是可以改进的点。

## 第 12 章 · web.py + ui.html：网页 Demo 是怎么转起来的

### 12.1 后端：一个 148 行的 HTTP 服务器

```python
def serve(engine, host="127.0.0.1", port=8000, open_browser=True):
    for candidate in range(port, port + 20):        # 8000~8019 依次尝试
        try:
            httpd = ThreadingHTTPServer((host, candidate), handler); port = candidate; break
        except OSError:
            continue                                 # 端口被占用，试下一个
    threading.Timer(0.6, lambda: webbrowser.open(url)).start()   # 0.6 秒后自动开浏览器
    httpd.serve_forever()                            # 阻塞，直到 Ctrl+C
```

三个值得学的细节：① **端口自动避让**（8000 被占用就试 8001…最多到 8019，你不用去查谁占了端口）；
② **`threading.Timer(0.6, ...)`** 延迟 0.6 秒再开浏览器，因为服务器可能还没完全启动好
（`lambda:` 是匿名函数，到点才执行）；③ **`serve_forever()` 是阻塞的**。

### 12.2 三个接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/` | 返回 `ui.html` 的全部内容 |
| GET | `/api/info` | 返回知识块数、文档列表、配置（给页面顶部徽章用） |
| POST | `/api/ask` | 收 `{"question": "..."}`，返回完整答案 JSON |
| GET | `/health` | 返回 `{"ok":true}`，给运维探活用 |

**GET 和 POST 的区别**：GET 是"我要拿东西"（参数在 URL 里），POST 是"我要提交东西"（参数在请求体里）。
提问要提交一段文字，所以用 POST。

### 12.3 处理一次提问

```python
def _build_payload(engine, question):
    started = time.time()
    with _LOCK:                          # ★ 串行化，见下
        ans = engine.answer(question)
    payload = ans.to_dict()
    payload["server_ms"] = int((time.time() - started) * 1000)
    payload["stats"] = {
        "chunks": len(engine.chunks),
        "docs": len({c.source for c in engine.chunks}),     # ★ 集合去重
        "answer_threshold": engine.cfg.answer_threshold,
        "llm": engine.cfg.use_llm,
        "embedding": engine.retriever.semantic_enabled,
        "corpus_dir": engine.cfg.corpus_dir,
    }
    log_answer(payload, extra={"channel": "web", "server_ms": payload["server_ms"]})
    return payload
```

**`len({c.source for c in engine.chunks})`** 这行值得单独讲：

- `{... for c in ...}` 叫**集合推导式**（set comprehension）；
- 集合自动去重，所以 `{c.source for c in chunks}` 就是"所有不重复的文件名"；
- `len(...)` 就是文档数。

比写一个循环 + `if source not in seen` 优雅得多。

**`with _LOCK:`** 是**线程锁**。原因写在注释里：

> 纯 Python 检索是 CPU 密集，串行化避免互相抢 GIL 导致延迟抖动

`ThreadingHTTPServer` 会为每个请求开一个线程。
Python 有个"全局解释器锁"（GIL），同一时刻只有一个线程能执行 Python 字节码。
两个请求同时在跑 BM25 时，会互相抢 GIL，导致**两者都变慢**（延迟抖动）。
加锁让它们排队，反而更稳定。**这是一个很小的语料下才成立的判断**——

> 如果语料变大到单次检索要几百毫秒，这个锁就会成为瓶颈，那时应该换成"预建索引 + 多进程"。

### 12.4 前端：一个 HTML 文件搞定

`ui.html` 的结构是标准的三大块：

```html
<style> ... 全部 CSS ... </style>
<body>
  <header> 标题 + 徽章 </header>
  <main> 示例按钮 + 结果区 + 输入框 </main>
  <script> ... 全部 JavaScript ... </script>
</body>
```

**没有任何构建步骤**：没有 npm、没有 webpack、没有 CDN。
双击就能跑，断网也能跑。这是刻意的（`web.py` 文件头解释了原因）。

三个 JS 环节：

**① 发请求**

```javascript
const r = await fetch("/api/ask", {
  method: "POST",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({question: q})
});
const d = await r.json();
```

`fetch` 是浏览器内置的 HTTP 客户端。
`await` 表示"等这个异步操作完成"（这一行会暂停，但页面不卡）。
`JSON.stringify` 把 JS 对象变成字符串，`r.json()` 把返回的字符串变回对象。

**② 转义 HTML（安全关键！）**

```javascript
function esc(s){
  return (s||"").replace(/&/g,"&amp;").replace(/</g,"&lt;").replace(/>/g,"&gt;");
}
```

**为什么必须转义？** 因为资料内容是外部输入。
如果不转义就把资料原样塞进 `innerHTML`，
那么资料里一段 `<script>alert(1)</script>` 就会在用户浏览器里执行——
这叫 **XSS（跨站脚本攻击）**。

注意转义的顺序：**先转 `&`**，否则后面转出来的 `&lt;` 里的 `&` 会被重复转义成 `&amp;lt;`。

**③ 引用编号可点击**

```javascript
function withCites(text){
  return esc(text).replace(/\[(\d+)\]/g, '<span class="cite" data-i="$1">[$1]</span>');
}
```

它把答案文本里的 `[1]`、`[2]` 变成可点击的 `<span>`。
`$1` 是正则里的**第一个捕获组**（也就是括号里的数字）。

点击时的行为：

```javascript
document.addEventListener("click", (e)=>{
  const c = e.target.closest(".cite"); if(!c) return;
  const card = c.closest(".qa"); const i = c.dataset.i;
  const src = card && card.querySelectorAll(".src")[parseInt(i,10)-1];
  if(src){ src.scrollIntoView({behavior:"smooth", block:"center"});
           src.style.borderColor = "var(--accent)";
           setTimeout(()=>src.style.borderColor = "var(--line)", 1400); }
});
```

**这段 10 行的代码实现了整个项目最有价值的交互**：

> 点答案里的 `[2]` → 页面平滑滚动到第 2 条引用 → 边框高亮 1.4 秒 → 你看到原文。

这就是 `CONTEXT.md` 里说的：

> 引用编号让"是否正确"从**信任问题**变成**核对问题**。

**`parseInt(i,10)-1`** 里的 `-1` 是因为人类从 1 数，数组从 0 数。
`addEventListener` 挂在 `document` 上而不是每个 `<span>` 上，
这叫**事件委托**——后插入的卡片也能响应点击。

## 第 13 章 · evaluate.py：怎么证明它真的行

### 13.1 为什么评测比代码更重要

这个项目最反直觉的一点：**`evaluate.py` 的价值不低于 `engine.py`。**

理由：如果没有评测，"我的系统效果不错"就只是一句主观判断。
这个项目里**三次**真实事故都是靠数字发现的：

1. 抽取式候选块数从 3 放宽到 5 → 覆盖率从 79.3% 掉到 69.0%（旧口径）；
2. 早期语料里 7 篇废弃文档没归档 → **硬答率高达 50%**（README 记录了这起事故）；
3. 拒答正文里的候选片段把覆盖率刷高 → 关键事实覆盖率 81.2% 是**假的**，真值 62.5%。

**没有数字，这三个问题都不会被发现。**
**但只有数字也不够**——第 3 个问题的数字本身"可复现"，却在算错的地方（见 13.6 纪律三）。

### 13.2 评测集长什么样

`data/logs/eval_set.json` 的结构：


每题有 5 个字段，各有用处：

| 字段 | 作用 |
| --- | --- |
| `id` | 题号，用于在报告里定位 |
| `question` | 问题本身 |
| `gold_source` | **期望命中的文档**（用于算 Hit@k、MRR） |
| `answerable` | **该不该答**（这是拒答准确率的关键） |
| `must_include` | **答案里必须出现的关键事实**（数字/术语） |

当前 22 题的分布（实跑统计）：`direct 8` 直问 + `paraphrase 6` 改写 + `multi_hop 2` 多跳 + `unanswerable 6` 必须拒答。

6 道应拒答题是**刻意设计**的，它们是这套评测集的灵魂：
**只考"能不能答对"的评测集，会奖励一个"什么都敢答"的系统。**

### 13.3 六个指标，各自回答一个问题

```python
for i, case in enumerate(cases, start=1):
    ans = engine.answer(case["question"])
    sources = [r["source"] for r in ans.retrieved]
    rank = 0
    if case.get("gold_source"):
        for idx, src in enumerate(sources, start=1):
            if src == case["gold_source"]:
                rank = idx          # ← 正确文档排在第几
                break
```

**① Hit@k** = "答案所在文档有没有出现在前 k 名里？" `hit_at_k = (0 < rank <= k)`
**为什么最重要**：**检索是 RAG 的上限**——正确文档没被检索出来，后面生成再厉害也没用。
本项目 Hit@3 = 100%，说明**检索环节没有丢失任何一道可答题**。

**② Hit@1** = 正确文档排第一的比例（81.2% = 13/16），衡量检索的精度。

**③ MRR** = 平均倒数排名，`reciprocal_rank = 1/rank`（排第 1 得 1.0、第 2 得 0.5、第 3 得 0.333）。
本项目 0.896。它比 Hit@1 细腻——因为"排第 2"也拿 0.5 分，而 Hit@1 只给 0 分，
**MRR 能体现"差一点就对了"**。

**④ 拒答准确率** = `refusal_correct = (refusal == (not answerable))`。
**唯一同时惩罚两类错误的指标**，所以最有代表性。本项目 77.3%。

**⑤ 硬答率** = `没拒答的应拒答题 / 所有应拒答题`。**全项目最关键的指标**，本项目 0.0%。

> 它和"拒答准确率"的区别：拒答准确率把两类错误合成一个数，
> 而硬答率**只统计最危险的那一类**——"该答却拒答"（漏答）只是体验差，
> "没料却硬答"是**会误导人的事故**。

**⑥ 关键事实覆盖率**：做法非常朴素——把答案里的空格去掉，看期望关键词在不在里面。

```python
def _term_coverage(answer, must_include):
    normalized = answer.replace(" ", "").lower()
    missing = [t for t in must_include if t.replace(" ", "").lower() not in normalized]
    return (len(must_include) - len(missing)) / len(must_include), missing
```

去掉空格所以 `"12 学时"` 和 `"12学时"` 都能匹配。实跑：n01 期望 `["23:00","23:30"]`，两个都在 → 100%。

**⚠️ 但这里有一个必须知道的坑：拒答必须单独计 0。**

```python
# campus_rag/evaluate.py 里的修法
refusal = ans.mode == "refusal"
coverage, missing = (0.0, []) if refusal else _term_coverage(ans.answer, must)
```

因为拒答的正文里会**原样引用检索到的候选片段**（"我检索到的、可能相关的片段如下…"），
而 `_term_coverage` 是在**整段回答**上做词面匹配——于是"该答却拒答"的题反而可能记满分。
这就是那个把覆盖率从真值 62.5% 抬高到 81.2% 的 bug（详见 13.6 和第 16 章）。

**为什么用这么土的方法？** 这是对 Faithfulness 的**廉价代理指标**——
用 LLM 当裁判更准，但要网络、要花钱、结果不可复现；土办法断网可跑、零成本、每次结果完全一样。
**取舍原则是"先要可复现，再要好"。**

### 13.4 报告长什么样

`format_report()` 把指标组织成四段：`【检索质量】【拒答能力】【答案质量】【分类别表现】`。
**最能定位问题的是"分类别表现"**（实跑）：

```
direct         n=8   Hit@3=100%  拒答准=75%  覆盖率=75%
multi_hop      n=2   Hit@3=100%  拒答准=50%  覆盖率=50%     ← 拖后腿
paraphrase     n=6   Hit@3=100%  拒答准=67%  覆盖率=50%     ← 拖后腿
unanswerable   n=6   Hit@3=0%    拒答准=100% 覆盖率=0%      ← 拒答一律计 0
```

一眼看出：**检索对四类都是 100%**（unanswerable 的 Hit@3=0% 正常，它没有 gold_source），
**漏答集中在"改写问法"和"多跳问法"两类**。
这就把"漏答率 31.2%"这个笼统数字**定位到了两类具体问题上**。

### 13.5 逐题明细与错误标注

```python
flag = "[OK]" if (r.refusal_correct and (not r.answerable or r.hit_at_k)) else "[X] "
f"  {flag} {r.id:<4} {mark:<6} mode={r.mode:<10} conf={r.confidence:.2f} "
```

`{r.id:<4}` 里的 `<4` 表示"左对齐、占 4 个字符宽"，让输出对齐成表——**做 CLI 工具的基本功**。
报告还会打印 `缺关键事实: 6 月`、`降级原因: HTTP 401（API key 无效）`。
**"缺关键事实"比一个百分比有用得多**——它直接告诉你缺的是哪个词。

### 13.6 三条重要纪律

**纪律一：评测必须能断网复现。** 文件头原话：
`注意：这里刻意不引入 LLM 作为评审（虽然更准），因为评测必须能在断网环境复现。`

**纪律二：不要用评测集去调参。**

这是 `docs/known-issues.md` 里那个非常成熟的判断（见 5.2 节）。
如果你用这 22 题去挑阈值，这 22 题就变成了训练集，
报出来的数字不再是"样本外"的，也就**失去了作为一个证据的价值**。

**纪律三（第二轮体检才学到的）：可复现 ≠ 正确。**

第一轮体检只核对了"README 的数字能不能用命令跑出来"，跑出来就结案了。
结果 81.2% 这个数字**确实可复现、却算错了**——它是在一段被拒答正文污染的文本上算的。
所以第二轮体检加了一条：**不仅要问"这个数字能复现吗"，还要问"这个数字是怎么算出来的"**。

## 第 14 章 · 三个实验脚本：sweep / calibrate / bench

这三个脚本不是"系统的一部分"，是**做实验的工具**。
它们的存在本身就是一种工程态度：**用指标做决策，不用感觉做决策。**

### 14.1 sweep.py：参数网格搜索

**它做什么**：把 `answer_threshold`（11 个值）× `evidence_k`（5 个值）= 55 种组合
各跑一遍完整评测，然后按优先级排序。

```python
thresholds = [round(0.30 + 0.02 * i, 2) for i in range(11)]   # 0.30 ~ 0.50
evidence_ks = [3, 4, 5, 6, 8]

for ek in evidence_ks:
    for th in thresholds:
        cfg = Config.from_env(answer_threshold=th, evidence_k=ek, use_llm=False)
        engine = RagEngine(chunks, config=cfg)
        report = run_eval(engine, cases, k=3)
        ...
```

**排序规则**（这是全项目价值观的代码化）：

```python
rows.sort(key=lambda r: (r[2], -r[3], -r[5]))
#                     ↑硬答率  ↑拒答准确率(负号=越大越前)  ↑覆盖率
```

`-r[3]` 的负号是因为 `sort` 默认**升序**，加负号就变成"值越大排越前"。

**注意"硬答率"排在第一顺位**：哪怕某个参数组合覆盖率更高，
只要硬答率不是 0，就排在后面。**这行代码就是"宁可拒答，绝不硬答"的数学表达。**

实跑结论：推荐 `answer_threshold=0.40, evidence_k=3`，但项目**决定不采纳**（原因见 5.2 节）。

### 14.2 calibrate.py：只看一条曲线

**它回答一个更尖锐的问题**：

> 同一套置信度公式下，可答题与不可答题的**分布**能不能被一个阈值分开？

它先打印每道题的分项信号（按置信度从低到高排）：

```
id   类别      conf   idf_cov   rare    oov  max_lex  spread    lex  问题
n10  可答     0.227   0.393  0.154  0.607   11.73  0.2832  0.456  有事要请假，最多能请多久？
nu05 应拒答   0.234   0.448  0.345  0.500   13.97  0.0161  0.499  补考没过的话最多能重修几次？

n09  可答     0.306   0.417  0.401  0.372   23.27  0.0393  0.624  住宿费里包了多少水电？用超了怎么算？

```

**这张表是调参的唯一依据**，但它同时暴露了一个**必须承认的事实**：
两组分布**在 0.23~0.42 这段是重叠的**——

- `n10`（可答，"请假最多能请多久"）只有 0.227，**比三道应拒答题还低**；
- `n09`（可答，住宿费水电）0.306，夹在 `nu01`(0.296) 和 `nu03`(0.331) 之间。

所以**不存在一个能完美分开两组的阈值**。你只能在"硬答"和"漏答"之间选一个权衡点。
本项目选了 `0.42`——它是**硬答率第一次变成 0 的最小阈值**，
代价是 `n10 / n09 / n11 / n14 / n16` 这些可答题被一起牺牲（漏答率 31.2%）。

> 面试时如果说"我用一个阈值把可答和应拒答完美分开了"，那是外行话。
> 正确的说法是："我算出了两组的分值分布，它们存在重叠区，
> 我在重叠区里选了偏向安全侧的那个边界，并且用指标量化了这个选择的代价。"

然后它做**阈值扫描**（0.18~0.68 共 51 个值）。
排序键 `key = (fa_rate == 0.0, acc, -over_rate)` 同样是"先硬答率为 0"；
最后它在"同等最优表现"的阈值区间里**取中点**，让阈值不贴着悬崖边：

```python
same = [f[3] for f in feasible if f[:3] == feasible[0][:3]]
chosen = round(sum(same) / len(same), 2)
```

**为什么取中点？** 如果最优表现对应 0.415，你选了 0.415，
语料稍变一点某个题的置信度掉到 0.414，就立刻硬答了。中点能留出**安全边际**。

**实跑出来的完整扫描曲线**（这条曲线的形状就是项目的灵魂）：

| 阈值 | 拒答准确率 | 漏答率 | **硬答率** | 覆盖率 |
| --- | --- | --- | --- | --- |
| 0.20 | 72.7% | 0.0% | **100.0%** | 90.6% |
| 0.25 | 77.3% | 6.2% | 66.7% | 84.4% |
| 0.35 | 81.8% | 12.5% | 33.3% | 78.1% |
| 0.40 | 77.3% | 25.0% | 16.7% | 65.6% |
| **0.42（默认）** | **77.3%** | **31.2%** | **0.0%** | **62.5%** |
| 0.50 | 50.0% | 68.8% | 0.0% | 31.2% |
| 0.60 | 36.4% | 87.5% | 0.0% | 12.5% |

- **阈值越低 → 越敢答 → 硬答率飙升**；
- **阈值越高 → 越保守 → 硬答率降到 0，但漏答率飙升、覆盖率同步下滑**
  （阈值越高拒答越多，而被拒答的题覆盖率一律计 0）；
- `0.42` 是硬答率第一次变成 0.0% 的**最小**阈值，往上调只牺牲漏答率、不改善安全性。

> ⚠️ 覆盖率这一列在 2026-10-06 修过口径。旧值（0.35→84.4%、0.42→**81.2%**、0.50→56.2%）
> 是被"拒答刷分"抬高的，看起来像"提到 0.42 覆盖率几乎不降"——那是假象，
> 降的全是被拒答的题，而它们在旧口径下反而记了满分。

**为什么不是更保守的 0.35？** 因为 0.35 时硬答率还有 33.3%——6 道应拒答题里有 2 道硬答了。
那两个学生会拿着编出来的校规去办事。**这是不可接受的。**

**为什么不在 0.42 和 0.45 之间再精细地找？** 因为 0.42 已经是"0 硬答"的最小值，
再往上是纯损失（漏答率从 31% 涨到 50%）。

### 14.3 bench.py：消融实验

**"消融"（ablation）**：**一次只去掉/改变一个因素，看结果怎么动**。
它的用途非常具体——**否掉"看起来更周到"的改动**。

```python
for n in (2, 3, 4, 5, 6):
    RagEngine.extractive_chunks = n              # ★ 直接改类属性
    engine = RagEngine(chunks, config=base)
    stats = fact_stats(engine, cases, 0.42)
```

`extractive_chunks` 是**类属性**（不是实例属性、也不是 config 字段），所以能直接在循环里改，
`RagEngine(...)` 出来的每个实例都用新值。**"方便做消融实验"就是它被设计成类属性的原因。**

bench.py 还提出了一个重要的**双口径**设计：

```python
"""两个口径，缺一不可：
- strict ：只统计真正作答了的题（拒答不算），衡量"答了的题答得准不准"
- end2end：以所有可答题为分母（该答却拒答 = 没覆盖），衡量"端到端到底解决了多少问题"
只看前者会高估系统——拒答更多时它会虚假变好。"""
```

极端例子：如果系统把所有题都拒答，`strict` 口径的分母是 0（或被定义成"完美"），
而 `end2end` 覆盖率是 0%。**只报 strict 口径的系统，可以通过"多拒答"刷分。**

实测实验一（**修 bug 后的新口径**）：候选块数 2 → 严格覆盖率 53.8%；**3 → 65.4%；4/5/6 仍是 65.4%**。
和本文 9.5.1 节的独立实测趋势一致，结论：`extractive_chunks = 3`。

> ⚠️ 但 `bench.fact_stats` 自己也曾经有两个 bug（2026-10-06 修掉）：
> ① 拒答题也进了 `strict` 的分母（与它自己的文档注释相反）；
> ② 实验二打印时两列都输出 `stats['strict']`，导致两列永远相等。
> **它宣称的双口径，实际没生效**——这正是"多拒答刷分"能藏住的原因。

实验二扫描阈值观察"端到端覆盖率 vs 硬答率"，和 `calibrate.py` 是同一问题的两个视角。

### 14.4 demo_check.py：防止"悄悄退化"

这是一个**回归测试**：把上台要演示的问题写好期望，每次改动后自动核对。

```python
DEMO_CASES = [
    ("南海校区宿舍晚上几点关门？周五周六和法定节假日会延后吗？", ["23:00", "23:30"], "08-"),
    ("旷课多少节会被警告处分？", ["12 学时"], "08-"),
    ...
    # 下面是"必须拒答"的用例 —— 现场演示的重头戏
    ("南海校区游泳池的开放时间和收费标准是什么？", [], None),
]

if must:      # 期望作答：关键词全中 + 来源对 + 不是拒答
    ok = all(m.replace(" ", "") in answer_norm for m in must) and (source in top_source) and ans.mode != "refusal"
else:         # must 为空 → 期望拒答
    ok = ans.mode == "refusal"
```

每个用例是三元组 `(问题, 答案里必须出现的关键词, 期望来源文档)`；`must` 为空表示期望拒答。

实跑：10 条全部通过（作答的 8 条 conf 0.47~0.68，必须拒答的 2 条 conf 0.30 / 0.25）。

**为什么必要？** 文件头的真实案例：

> 我改了检索/抽取逻辑后，某些问题会悄悄退化
> （实测"挑战杯奖金"从正确摘录退化成引到"竞赛分级"那一节）。靠眼睛看一眼是发现不了的。

**它和 `ask.py --eval` 的分工**：

| | demo_check.py | ask.py --eval |
| --- | --- | --- |
| 题量 | 10 条（精挑） | 22 条 |
| 判断标准 | 硬性关键词（对/错） | 百分比指标 |
| 用途 | **防止演示翻车** | **衡量整体水平** |
| 退出码 | 有失败则返回 1 | 总是 0 |

`return 1` 很重要：它让**自动化脚本能够感知失败**。
`docs/known-issues.md` 里最深刻的教训就是这个：

> **没有任何命令的失败被检查** —— 路径写错后，`--eval` 直接崩，但没人跑它。

| # | 位置 | 错在哪 | 后果 |
| --- | --- | --- | --- |
| 1 | `retriever.expand_query` | 拿 `tokenize()` 的输出当同义词表的 key，而分词只产出 CJK bigram/unigram → **3 字以上的词条永远不可能命中**（"多少钱""收费标准""申请条件"…） | "同义词扩召回"这条设计实际从未生效 |
| 2 | `evaluate.run_eval` | 拒答正文里原样引用了候选片段，而覆盖率在**整段回答**上做词面匹配 | `n09`/`n11`/`n14` 三条该答却拒答的题覆盖率记 100%，覆盖率被抬到 81.2%（真值 62.5%）；`sweep.py` 还拿这个指标挑阈值 = **奖励"拒答但带出处"** |
| 3 | `bench.fact_stats` | 拒答题进了 `strict` 分母；实验二两列都打印 `strict` | 双口径形同虚设，"多拒答"的虚假提升看不出来 |
| 4 | `ask.cmd_chat` | `show_trace=q.startswith(":s") or True` —— **恒真表达式** | 帮助里写的":s 查看检索详情"根本不存在，而检索详情又永远开着 |

**修完之后检索指标一个没动**（Hit@3 100% / Hit@1 81.2% / MRR 0.896 / 硬答率 0.0%），
只有被 bug 污染的那个数字变了：关键事实覆盖率 81.2% → **62.5%**。

> **默认阈值仍然不动。** 检索逻辑变了、分数分布变了，按纪律本该重跑 `sweep.py` 重标定——
> 但"不用评测集调参"这条纪律优先级更高。**这次的 62.5% 同样是样本外指标。**

**这一节是全项目最值得读的一节**，因为它讲的不是"我写了什么功能"，
而是"我发现自己的功能其实没生效，并且给它补上了防线"。

### 14.6 当前已知的三处不完美（诚实清单）

| 位置 | 现象 | 影响 |
| --- | --- | --- |

### 套路 2：答案不对，怎么定位是哪一环出的问题？

```powershell
python ask.py "你的问题"      # 看输出最后的 [检索轨迹] 和 [引用来源]
```

| 现象 | 问题在哪 |
| --- | --- |
| 正确文档**没出现在引用来源里** | `retriever.py`（分词 / 切块 / 融合） |
| 出现在前几名但**被拒答了** | `engine._confidence`（阈值 / 信号） |
| 作答了但**答非所问** | `_extractive`（选句）或提示词（LLM 模式） |

要看得更细：`python calibrate.py` 会打印**每一道题**的 `idf_cov / rare / oov / max_lex / spread / lex`；
问题不在评测集里就打印 `ans.trace`，或直接 `python ask.py "问题" --json`（最完整的一手信息，
含 `retrieved`：所有检索结果 + 每个通道的分数）。

### 套路 3：改了代码后，怎么确认没有退化

`AGENTS.md` 要求的流程（README 第 10 节同）。**按顺序跑这五条**：

```powershell
python -m unittest discover -s tests -v   # ⓪ 回归测试：曾是 bug 的路径不许复活（★ 新增）
python demo_check.py    # ① 10 条演示用例是否条条正确（含 2 条必须拒答）
python ask.py --eval    # ② 核心指标是否守住：硬答率必须为 0
python bench.py         # ③ 消融实验：这项改动到底有没有用（严格/端到端两个口径都要看）
python sweep.py         # ④ 改了分词/检索后，阈值要重新标定（分数分布变了）
```

**判断标准**：**硬答率 > 0 视为失败**；在这个前提下再比拒答准确率与覆盖率。
而且 ⓪①②③ 都要看**退出码**——这个项目上一次翻车，正是因为"没有任何命令的失败被检查"。

第 ④ 条的理由很多新手想不到：置信度公式里用到 IDF，**改了分词就改变了所有题的置信度分布**，
原来的 0.42 可能不再卡在"恰好 0 硬答"的位置。

### 套路 4：换一份自己的语料

```powershell
python ask.py --corpus "D:\我的资料" --info      # 先看块数，确认加载成功
python ask.py --corpus "D:\我的资料" --web       # 起网页
python sweep.py --corpus "D:\我的资料"           # ★ 换语料后必须重标定阈值
```

格式建议：用**带标题**的 `.md`（切块按标题切）；表格用标准 Markdown 表格（会被表头回填改造）；
一份文档讲一个主题。

**最容易忽略的一步就是重标定**：换了语料还用旧阈值，硬答率很可能不再是 0。

### 套路 5：按 `mode` 分类看日志

```powershell
# 今天的日志里，有多少是拒答？
python -c "import json;[print(json.loads(l)['mode'], json.loads(l)['question'][:30]) for l in open('data/logs/qa_2026-09-17.jsonl',encoding='utf-8')]"
```

日志格式（每天一个文件，每行一条 JSON）：

```json
{"ts": "2026-09-17T21:30:12", "question": "宿舍几点关门？", "answer": "...",
 "mode": "extractive", "confidence": 0.5609, "latency_ms": 0,

 "channel": "web", "server_ms": 12}
```

**`qa_logger.py` 采用的工程做法值得学**：

```python
_LOCK = threading.Lock()           # 多线程写文件必须加锁

def log_answer(payload, log_dir=..., extra=None):
    try:
        ...
        with _LOCK:
            with path.open("a", encoding="utf-8") as f:
```

注释里说明了为什么用 **JSONL**（每行一个 JSON）而不是一个大 JSON 数组：

以及那个 `except Exception: return None`：

> 容错原则：日志失败绝不能影响主流程——问答是主路径，日志是旁路。

**"主路径"和"旁路"的区分**是一个成熟的架构意识。

### 套路 6：`git` 的用法（`AGENTS.md` 明确要求）

项目规定：

> 每次改动完成后，都必须创建一个对应的 Git commit，以便后续追踪和回滚。
> 每次改动后，都必须编写或更新相关测试，并在交付给用户前，确保所有测试和验证全部通过。

最小工作流：

```powershell
git status                    # 看改了哪些文件
git diff                      # 看具体改了哪几行
python demo_check.py          # 先确认没退化
python ask.py --eval          # 再确认指标守住了
git add -A
git commit -m "fix: 修正 xxx（原因）"
```

**为什么"每次改动一个 commit"很重要？** 因为当你发现"改了之后指标掉了"，
你需要能**精确地回到上一个好状态**。如果一次 commit 里塞了 10 个改动，
你根本不知道是哪个改动造成的（这正是 `bench.py` 消融实验要解决的问题）。

`git log --oneline` 看一下这个项目的真实历史，你会看到很多这样的 commit：

```
7467737 docs: README 指标改为实测值；体检报告结案；新增 ADR-0001（选择用 AI 派）
3872216 fix: 恢复 README 指标的可知复现性（语料归位 + 评测集重建 + 报告默认写出）
4216e78 fix: --eval-set 默认路径改为 data/logs/（原路径 data/eval_set.json 从不存在…）
```

**注意 commit message 的写法**：`类型: 一句话说清做了什么 + 为什么`。
`fix:` / `docs:` 这种前缀叫 Conventional Commits，是行业惯例。

### 套路 7：读懂报错

新手最怕报错，其实报错信息**读法是有套路的**：从下往上看。

```
Traceback (most recent call last):
  File "ask.py", line 245, in main            ← ① 最先出错的地方在最下面
    engine = build_engine(args)
  File "ask.py", line 75, in build_engine
    chunks = load_corpus(cfg.corpus_dir, ...)
  File "campus_rag\data.py", line 184, in load_corpus
    raise FileNotFoundError(f"语料目录不存在: {root}")   ← ② 真正的错误在这
FileNotFoundError: 语料目录不存在: D:\不存在的路径        ← ③ 错误类型 + 消息
```

三个信息：

1. **最下面一行**是错误类型和消息（`FileNotFoundError: 语料目录不存在: ...`）；
2. **往上一行**是真正出错的那句代码（`raise ...`）；
3. **中间的每一层**是"谁调用了谁"（调用栈）。

所以正确读法是：**先读最后一行搞清"什么错"，再往上看"哪里错"。**

### 套路 8（附加）：三个最可能踩的坑

**坑 1：中文乱码**

Windows 控制台默认 GBK。解决方案：`chcp 65001` 或在脚本里 `reconfigure(encoding="utf-8")`。
`ask.py` 的 `_use_utf8_console()` 就是在自动干这事。

**坑 2：`ModuleNotFoundError: No module named 'campus_rag'`**

原因：你没在项目根目录运行，或者脚本开头少了 `sys.path.insert(...)`。
解决方案：`cd` 到项目根，或在脚本里加上那两行。

**坑 3：改了阈值但没生效**

原因：`argparse` 里的 `--threshold` 默认值和 `config.py` 里的默认值**是两个地方**。
`ask.py` 会用 `args.threshold` **覆盖** config 的值。
改的时候要一起改，或者直接用命令行传：

```powershell
python ask.py --threshold 0.50 "你的问题"
```

## 第 17 章 · 面试怎么讲这个项目

`docs/roadmap.md` 里提出了一个很好的自检工具——**向上追问三层**：

| 层 | 问题 | 合格标准 |
| --- | --- | --- |
| 第 1 层 | **这是什么？** | 能用一句话说清它在干什么 |
| 第 2 层 | **为什么这么写？** | 能说出替代方案，以及为什么没选它 |
| 第 3 层 | **如果去掉它 / 换掉它会怎样？** | 能预测后果，**或者说"我不知道，但我可以这样验证"** |

下面用第 2/3 层（第 1 层"是什么"就是前面各章的标题）整理成可以直接背的讲法：

| 决策 | 第 2 层：为什么不用替代方案 | 第 3 层：去掉/换掉会怎样 |
| --- | --- | --- |
| **1. bigram+单字** 代替 jieba | jieba 精度更高但要 `pip install`；项目要求"断网也能跑"。这也是 Lucene `CJKBigramFilter` 的官方做法 | 去掉单字：文档里的双字词无法被单字查询匹配（"金额" vs "奖励标准"），直接漏检。单字 IDF 天然很低，所以不污染排序 |
| **2. 两通道 + RRF** | 也可加权求和，但 BM25 是 65.88、余弦是 0.0889，**量纲不可比**，归一化本身又引入超参数 | RRF 丢掉了分数信息（第 1 名 0.0164 vs 第 2 名 0.0161），所以**不能拿它当置信度**——这就是要另算一套的原因 |
| **3. 闸门前置于生成** | 也可让模型看资料后自己判断，但模型有"必须给出像样回答"的倾向，实测会硬答；闸门判断是**确定性、可评测**的 | 早期版本（v0）没有闸门，在早期 7 篇语料上硬答率 **83.3%**（过程记录，非当前指标；当前 0.0%） |
| **4. IDF 加权置信度** | 朴素覆盖率把"什么/多少"算成证据 → 没料也硬答；IDF 加权后只有实词计入分母 | 副作用是**越稀有 IDF 越高**（"水温"只出现 1 次），所以要再加稀有词惩罚。**两层互相制衡** |
| **5. 表格表头回填** | 数据行 `\| 本科生 \| 15 册 \| 30 天 \|` 里没有"可借册数""借期"，它们全在表头，切块后必然漏检 | 不做就误判为"证据不足"而拒答；做完 Hit@1 有明确提升（README：当时"直接把 Hit@1 推到了 100%"） |
| **6. 参数能更好看但不调** | `sweep.py` 建议 `0.40/3` 指标更好，但评测集刚建——用它调参它就变成训练集，数字不再样本外 | 正确顺序：**先扩到 100+ 题 → 再分层看指标 → 最后才调参**。结论留档 `docs/known-issues.md` |

### 附：面试时最容易被追问的五个技术细节

1. **`evidence_k` 和 `top_k` 为什么要分开？**
   → 多跳问题的证据常分散在第 4~6 名，用生成块的窄视野判断会导致误拒。
   （配实测数据：`evidence_k=1` 时漏答率 62.5%，`=5` 时降到 31.2%。）

2. **RRF 里的 `k=60` 是什么意思？**
   → 平滑常数。`1/(k+rank)` 让第 1 名和第 2 名差距很小，
   从而让"多条通道的共识"比"单条通道的第一名"更重要。

3. **OOV 惩罚是怎么算的？**
   → 查询词里语料中不存在的那些，按 2.0 的虚拟 IDF 计入信息量总量，
   然后 `base *= 1 - 0.85 * oov_share`。
   这是区分"用词不同"（能答）和"概念不存在"（该拒答）的唯一非词法依据。

4. **为什么评测不用 LLM 当裁判？**
   → 评测必须能在断网环境复现、零成本、结果稳定。
   用 LLM 判官更准，但引入网络依赖和不可复现性。
   生产环境应该补 RAGAS 的 Faithfulness / Answer Relevancy。

5. **如果语料从 63 块扩到 10 万块，哪里会先崩？**
   → `BM25` 和 `TfidfVector` 都是在内存里暴力遍历/全表算分，
   10 万块时单次检索会从 3ms 涨到秒级。
   解法是倒排索引落盘 + ANN（HNSW/IVF）近似最近邻，
   **`retriever.py` 的接口不用改，换实现即可**——
   这也是当初把检索层单独抽成一个类的价值。

| 术语 | 意思 | 代码位置 |

| **语义通道 (Semantic Channel)** | 可选 embedding 通道，没配置时系统照样完整工作 | `retriever._semantic_scores` |

| **生成块 / 证据块** | `top_k`=送进生成的块数；`evidence_k`=判断该不该拒答的块数 | `config.py` |
| **拒答 (Refusal)** | 系统判断"资料不支持该问题"后的输出，是**正确行为** | `mode="refusal"` |
| **漏答 (Missed Answer)** | 资料里有答案但系统拒答了，是闸门的**代价** | `over_refusal_rate` |
| **接地提示词** | 约束模型"只能用给定资料说话、必须标注来源" | `engine.SYSTEM_PROMPT` |
| **引用编号 (Citation Marker)** | 答案中形如 `[n]` 的来源标注 | `ui.html` 的 `withCites` |
| **抽取式降级** | 模型不可用时，从原文挑句子原样摘录 | `engine._extractive` |
| **硬答 (Hard Answer)** | 资料里没有却给出言之凿凿的回答，**最不可接受** | `false_answer_rate` |
| **关键事实覆盖率** | 回答中包含期望数字/术语的比例（**只用于真正作答的文本**；拒答在 `run_eval` 里直接计 0） | `evaluate._term_coverage` |
| **消融实验 (Ablation)** | 一次只改一个因素，看指标怎么动 | `bench.py` |
| **参数网格搜索** | 在评测集上扫参数组合，按约定优先级挑最优 | `sweep.py` |
| **回归测试** | 把修过的 bug 逐条钉住，不许复活 | `tests/test_regressions.py` |
