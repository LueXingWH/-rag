## 问题 1｜`ask.py --eval` 直接崩溃 ✅ 已修复

**现象**

```
FileNotFoundError: [Errno 2] No such file or directory:
  '...\my__ai\data\eval_set.json'
```

**根因**：`ask.py` / `bench.py` / `calibrate.py` / `sweep.py` 四处把评测集默认路径写成

也就是说：README 首推的"一条命令复现指标"从某个时间点起就已失效，而没人发现——**因为没有任何自动化在跑它**。

**修复**：四个文件的默认路径改为 `data/logs/eval_set.json`；README 目录树同步更正。

## 附：为什么这四个问题之前没被发现

1. **没有任何自动化在核对 README 与实测值** —— `demo_check.py` 只校验 10 个**手工挑选**的演示用例，
   它们全部通过；它不读 README，也不跑完整评测集。
2. **`demo_check.py` 与 `ask.py --eval` 用不同语料** —— 一个绿、一个红，但没人同时跑，矛盾一直没暴露。
3. **评测集从 22 题缩到 10 题没有同步文档** —— 数字变了，叙述没变。
4. **没有任何命令的失败被检查** —— 路径写错后，`--eval` 直接崩，但没人跑它。

## 刻意没有做的一件事：**没有**用新评测集重新调阈值

`sweep.py --coarse` 给出的建议是 `answer_threshold=0.40, evidence_k=3`（当前默认是 `0.42 / evidence_k=5`）。

**为什么不改**：这套 22 题评测集是**刚建好的**。如果现在用它去挑阈值，
阈值就变成了"**拟合这个测试集**"，之后报出来的所有指标都不再是样本外的。
README §7 第 3 条已经承认过这个过拟合风险——承认了就该避开它，而不是利用它。

**所以当前状态的定位是**：

- 阈值 `0.42 / evidence_k=5` 是在**早期语料版本**上标定的；
- 本轮上面的 77.3% / 31.2% / **0.0%**，是在新语料 + 新评测集上测得的、
  **真正的样本外指标**。

这比"调完阈值后的漂亮数字"更可信，面试时也是更好的故事：
**"我重建了评测集，但我没有拿它调参——那样它就变成测试集了。"**

**要改进漏答率，正确顺序是**：先把评测集从 22 题扩到 100+ 题 → 再分层看指标 → 最后才谈调参。
`sweep.py` 的这条结论留档在此供日后参考，**不作为当前默认值**。

# 第二轮体检（2026-10-06）：四个真 bug

`python ask.py --eval`，同一套语料与 22 题评测集：

## bug 1｜同义词扩展是一张死表 ✅ 已修复

**现象**：`SYNONYMS` 里 3 字以上的词条**永远不会命中**。

```python
>>> expand_query("四六级报名要交多少钱？")
[]                     # 修前
['标准 元 费用 收费标准']  # 修后
```

**根因**：`expand_query` 拿 `tokenize()` 的输出当查表的 key，而分词只产出
CJK **bigram/unigram** 和英文词——"多少钱""收费标准""申请条件""国家奖学金"这类词条
永远不可能等于某个 token。表里 22 个 key，其中 16 个是 2 字（能命中），
其余的长词条全是死代码。

**讽刺之处**：README §5 把"同义词扩召回"写成一条设计决策，注释还专门写了
"口语问法 → 文档用词"——注释描述的正是那些**不可能生效**的词条。

**修复**：改为对原始查询做**子串匹配**（与分词结果解耦）。子串匹配是原 token 匹配的**超集**，
既有行为不丢。新增不变式测试：**表里每一条都必须能触发**。

## bug 2｜拒答文本把"关键事实覆盖率"刷成了满分 ✅ 已修复

**现象**：三条**该答却拒答**的题，覆盖率记了 100%：

| 题 | 期望关键事实 | 修前覆盖率 | 实际状态 |
| --- | --- | --- | --- |
| n09 住宿费里包了多少水电？ | 8 千瓦时 / 4 立方水 | **100%** | 拒答 ❌ |
| n11 学校的处分都有哪几档？ | 留校察看 / 开除学籍 | **100%** | 拒答 ❌ |
| n14 四六级报名要交多少钱？ | 36 元 | **100%** | 拒答 ❌ |

**根因**：拒答模板会把检索到的候选片段原样打进 `answer`：

```
资料中没有找到足够相关的内容…
  [候选1] 09-…问答.md · 宿舍与住宿：… 每月 8 千瓦时、4 立方水 …
```

而 `_term_coverage` 是在**整段回答**上做词面匹配。于是"没答出来"反而因为
"引用了含答案的片段"而拿满分——**指标自己把拒答奖励了一遍**。

**连锁影响（比数字本身严重）**：`sweep.py` 用 `answer_coverage` 排序挑阈值，
等于在优选中**奖励"拒答但带出处"**的参数。

**修复**：拒答一律计 0（`run_eval` 里判定，`_term_coverage` 只用于真正作答的文本）。
README 的 81.2% → **62.5%**；`bench.py` 早就在用更严的口径（65.4%），修复后两条链路互相印证。

## bug 3｜`bench.py` 的两个口径算出来是同一个数 ✅ 已修复

**现象**：`bench.py` 实验二的"端到端覆盖率"和"严格覆盖率"**两列永远相等**。

**根因（两处叠加）**：
1. `fact_stats` 里拒答题也计进了 `strict` 的分母（与它自己的 docstring 相反）；
2. 打印时第 89 行把 `stats['strict']` 输出了**两次**。

**为什么危险**：`strict` 的口径本该是"答了的题答得准不准"。一旦拒答题进了分母，
**"多拒答"就会让指标变好看**——消融实验正好失去它唯一的作用：戳穿这种虚假提升。

**修复**：两个口径真正分开（`strict` 只含作答题、`end2end` 分母含拒答题），
并按 `ans.mode` 而不是"置信度 < 传进来的阈值"判定拒答——同一件事不该在两处各实现一遍。

## bug 4｜`:s` 是假的命令，`trace` 恒开 ✅ 已修复

**现象**：`--chat` 的帮助写着":s 查看检索详情"，但这行代码是：

```python
print(render_answer(ans, show_trace=q.startswith(":s") or True))   # 恒真
```

`:s` 既不是命令（输入 `:s 宿舍` 会被整串丢去检索），检索详情又永远开着。

**修复**：把命令解析抽成纯函数 `parse_chat_command()`（quit / help / toggle_trace / ask / empty），
`:s` 成为真正的开关，并补了"以 `:s` 开头的**问题**不能被命令吃掉"的测试。

## 这一轮的教训

1. **上一轮只对齐了数字，没检查数字是怎么算出来的。** 81.2% 被核对了两次都没发现问题——
   因为它确实是可以复现的，只是**不该被那样计算**。可复现 ≠ 正确。
2. **指标 bug 比代码 bug 更贵。** bug 2 会让 `sweep.py` 主动挑出更爱拒答的参数，
   而它给的每一个数字都看起来"有出处"。
3. **凡是"帮助文本"与"代码"说的不一致，先怀疑代码。** bug 4 的 `or True` 是最典型的形状：
   写得像有逻辑，其实恒真。
4. **能靠测试钉住的，别靠记性。** 这四个 bug 现在各有一条测试；
   其中 bug 1 用的是**不变式**（"表里每一条都必须能触发"），而不是逐个词条断言——
   这样以后往表里加新词条时，漏了匹配方式会立刻红。

> 与上一轮同一个结论：**这四条本身就是面试素材。**
> 能讲清"我的指标被自己的拒答文本刷了分，而我是怎么发现的"，
> 比报一个更高的覆盖率可信得多。
